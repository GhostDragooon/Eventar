# MVP acceptance walk: one open MAJOR or red gate means not done

Declare the MVP complete only when every checklist row passes on the final HEAD with evidence. One open BLOCKER or MAJOR, one red gate, or one unrun row keeps it open. Lead with the verdict. A red gate that predates the base still counts: the verdict names it and gives its hit count. Never write "every gate is green except" a listed failure, and never let a verdict sentence about "done" leave out a red gate that is in the table.

- Preflight before any walk or lens dispatch: run `git status --short` untruncated and split it into `.claude/skills/` paths and product paths (`app/`, `components/`, `lib/`). If product paths are modified and neither the latest handoff nor `docs/plans/PROJECT_STATE.md` names them, stop and get Ivan's ruling (review the diff, walk as is, or park it) before walking. Every PASS on an unnamed uncommitted tree carries a caveat. Report `.claude/skills/` changes on their own line, never inside the product count, and never filter them out silently with `grep -v`.
- Before the walk, run `pnpm check:ui-primitives` and `pnpm check:ui-colours`, then attribute each hit to HEAD by its line text with `git show HEAD:<file> | grep -n '<pattern>'`. Name the hits that predate the base. Do not describe a hit as pre-existing until that check has run.

Hard rule: nothing dies in silence. A quiet data change, a dead-end instruction, or a partial write with no plain recovery path is a MAJOR. Triage each into fix-now (tied to a named ruling) or defer (written in the summary with its reason and the stage it waits for). A deferred item is never reported as fixed.

- Tag each checklist row: [X] executed this run, [R] read in code, [I] inferred. A row without an [X] tag is not a pass.
- Re-run each headline MAJOR yourself before presenting it. Name the MAJORs that rest only on an agent's run.
- Order the work so the walk judges final copy. Run the reviewers and the backtest read-only first, then one fix wave, then the full gate chain, and run the user-lens walk last. Do not edit copy while a backtest greps exact strings: the edit invalidates its checks, and hot reload changes pages mid-walk.
- Run the gate chain on the final tip per `eventar-static-gates`. Quote live `check:ui-*` counts, never the handoff's; label each hit that predates the base commit.
- A step an agent did not reach at its cap is a gap. If you run it yourself, mark it orchestrator-executed with its evidence; never add it to the agent's PASS count. Take a window-critical step over yourself when the lens's cap went to tooling (pane wake, a slow picker, a hidden pane) before the step's own outcome. Run it with `browser_batch` in small batches, one batch per window state, and read back the DB row after each click.
- A subset vitest run is a spot check. Say so; never write "gates green" for it.
- Screenshots: list per step whether the image is on disk. "Inspected inline" is not a screenshot.
- A walk row names the actor relation it tests. A creator-only path (publish, edit) walked as the event's creator passes for the creator alone. Walk it again as a non-creator member before writing PASS, or write `PASS [X: creator only]` and name the untested path. On 2026-11-06 the publish row was walked by the creator, so the non-creator publish path was left untested. A landing or redirect row also names its entry path: entering through an event page does not test a cold start from `/login` with no `next`. On 2026-11-14 the practitioner lens came in via an event page, so its "Done" landing was not the cold-start case, and the roles lens walked that case separately.
- Briefs copy the sign-in, mail-catcher and fixture recipes from `eventar-live-verify-worktree`; never retype them from memory. On 2026-11-03 the first organiser brief gave an Inbucket mailbox path on :54324, and the lead's correction named Mailpit (`/api/v1/messages`), so the lens lost calls before its first sign-in.
- Run each persona walk as a dispatched lens, with cheaper-model dispatches for its mechanical steps (see `subagent-dispatch`), not inline on the main model. On 2026-11-15 both persona walks ran inline, and the 5-hour limit cut the turn off twice before the walk report existed.
- Browser lens briefs open with the pane wake, not with the walk: `tabs_context`, `tabs_select` on the seed tab, one screenshot, then confirm `read_page` returns elements. On 2026-11-03 three lenses ran on a hidden pane, got empty reads, and fell back to synthetic events, so their dead-control findings were unprovable. If reads stay empty after the wake, the lens records a gap and does not click through `dispatchEvent` or `form_input`.
- Browser lenses share one cookie jar, so run persona walks one after another (organiser, then practitioner, then roles), never in parallel. Each lens clears stale cookies before its own sign-in and ends with the app's own Sign out. Parallel sign-ins collide on the server session. On 2026-11-21 the practitioner lens was held until the organiser lens returned.
- One `docs/plans/mvp/REVIEW-FINAL-<lens>.md` per lens, plus `REVIEW-FINAL-summary.md` with the checklist table. Each lens reads and writes only its own file.
- A consent or agreement sentence that names a document with no page (Terms, Privacy, a policy) is a MAJOR dead end: the user is asked to accept what they cannot open. Walk each link in the copy, read the status, and either publish a reviewed page or reword the sentence. Record it as a finding with the exact sentence. On 2026-11-03 the practitioner wizard asked for acceptance of Terms and Privacy with no pages behind them.
- A wrong-turn input (whitespace-only name, unticked consent, invalid email, empty guest name) gets its own row. A greyed submit with no reason in words is a finding under `disabled-control-explains-why`. On 2026-11-14 a whitespace-only name left Register greyed with no reason, and the invalid-email, duplicate and empty-guest-name turns were left NOT RUN.
- A finding that survives a round unfixed is not re-reported as a MINOR or NIT. Name the round it first appeared in, and put it to Ivan as a ruling with its options and what each costs. Any option that changes copy or a page ships its rendered before and after first, as a live published Artifact with controls, per `design-decision-specimen-round`. A ruling question with no frames attached is a violation, even when the answer looks obvious. On 2026-11-21 the r4 practitioner lens re-reported the greyed Register button with no reason for an empty name ("m3 ... (r3, unfixed)") and the consent sentence with no page behind it (MAJOR, first flagged 2026-11-03, still unfixed).
- Rows for PROJECT_STATE, vault and graph stay NOT RUN until Ivan rules on the findings. Do not commit, stage or push the review files without his go.
- A time-gated surface (check-in desk, registration window) is walked in three states, not one: before the window, inside it, after it. Move the fixture's `start_time` and `end_time` (and its `event_occurrences` row) to each state with a helper, reload, and read the gate's status copy and enabled controls. Read back `registration_checkins` rows after each click, and confirm the expected row count per state. Keep the state-shift helper in the skill's `scripts/` or the walk's own run sheet; a helper left only in the session scratchpad is gone for the next walk.
- A "no response" finding on a control is kept only after the orchestrator re-clicks it and reads the whole page below the control row. On 2026-11-03 a lens reported `+ Walk-in` giving no response while the window was closed; the orchestrator's re-click showed a panel under the control row saying check-in has not opened. The lens had read a hidden pane. Downgrade or drop the finding and say why in the file.
- After any walk-in or guest check-in made while signed in as staff, read the row back: `source`, `status`, `check_in_method`, `user_id` and `profile_snapshot`. A walk-in row must have `user_id` null and `profile_snapshot` null, and the staff row id and auth user id must appear in no attendee column. Any staff identifier on the attendee row is a MAJOR under hard rule 1, even when the screen looks right.
- A closed-window gate is tested on every write path into the same table, not only the desk the lens was given. Enumerate the writers (grep the Server Actions that insert into `registration_checkins` and `speaker_checkins`), then in the before-window state attempt each one and read back the row count. On 2026-11-03 the attendee desk refused a check-in while closed, but a speaker check-in wrote a `speaker_checkins` row 31 days before the event with no error. That is a MAJOR under the window rule, even though the desk the lens walked was correct.
- The S7 CSV check runs on the registrants export, not the analytics export. The analytics "Export CSV" is the funnel summary (`Section,Item,Count,Percent`) and never holds registrant names. Export the registrants list for an ended event, with a fixture named `=HYPERLINK(...)`, and read the cell back. On 2026-11-14 the organiser lens marked this row NOT RUN because it read the funnel file.
- A window-shift helper must move the event's `agenda_blocks` too. The S5 trigger refuses any block outside the event window, so a helper that moves only `events` and `event_occurrences` breaks on every event with blocks. On 2026-11-14 `walk-window.sh` failed this way, and the helper lived in an untracked skill folder.
- A capacity or last-seat race is walked by filling the last seat with SQL while the form stays open, then clicking submit. Expect the inline refusal (for example "This event is at capacity.") and read back the row count: it must not change. On 2026-11-14 the practitioner lens ran this and got the inline refusal, 0 rows written, count 1.
- Before the summary says who ran a lens or review (for example, dev and user reviews as separate agents), check the dispatch record in the transcript, not compressed notes. Before quoting a count from `git status` or any output that was cut short, re-run it untruncated. On 2026-11-15 both claims were checked only at wrap-up, and one count was softened because it was unverified.
- A pause request ("pause when possible", "a plan other agent can pick up") stops at the next checkpoint: start no new batch and no new dispatch. Before stopping: (1) write the walk report and each lens's findings to a file under `docs/plans/mvp/` in the repo, never only to the transcript or a tool-results file; (2) add a `Status at pause` section that names what ran, what has not started, the next step by name, and every local fixture id with its delete order; (3) stop each dev server you started and confirm its listener is gone with `lsof`; (4) delete scratch key files. On 2026-11-16 the walk report lived only in the transcript, and the 56 KB string sweep sat in a tool-results folder outside the repo, so the next agent could not open either from the repo.
