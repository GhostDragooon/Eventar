# An undecided frontend surface is answered by a specimen round, not by a built screen

Show it live, never as a sketch. For any frontend change, render the page in the Browser pane on the worktree's :3100 and show Ivan the frames. Do not draw a visualize widget that stands in for the page: Ivan asked for live frames from 2026-11-20 on. Two paths: (a) a choice among several options goes to the specimen route below, and product code waits for his pick; (b) a single approved fix or a mechanical change to an existing pattern is rendered first: send Ivan the before frame, then apply on :3100, reload, and send the after frame with the measured values that back it. Never apply and send the render afterwards, and never ask "apply?" with only a code diff. This holds even when the change is mechanical. Name what the frame shows.
Deliver each frame as a file with SendUserFile, in the same turn as the edit. A Browser-pane screenshot seen only in the transcript does not count as delivery. Take the before frame before the first source edit. Once the edit is in the tree, the live page shows only the after: then render HEAD in a separate worktree for the before, or simulate it per the simulated-before rule below, and say which. An after-only pair is a violation, not a partial pass. Write frames to an absolute path in the scratchpad, never the repo root. Do not write "done" on a frontend edit until both frames are delivered. A one-class fix gets the same before and after pair as a redesign.

Run the locked pipeline in `~/.claude/CLAUDE.md` first when the choice is a design decision, then show every candidate as a labelled option on one dev-only specimen route. Ivan picks. The code does not.

The decision surface is a published Artifact, not a screenshot. Ivan, 2026-11-21: "render all this in artifact so i can interact, not screenshots". Write one self-contained HTML file in the scratchpad that shows the real before and after of each option, with live controls (width slider, presets, theme toggle, hover and focus states). Copy the real tokens from `app/globals.css`. Publish it with the Artifact tool and give Ivan the link. Screenshots stay as proof frames of an applied edit only. A render with no live control is not a decision render.

- Route: a dev-only page under `app/dev-preview-uiport/`, gated out of production by the sandbox layout. Specimens use sample data and wire nothing into product screens. If the `show_pane` call answers that the session is not open in any window, the pane is not shown: put the exact URL and the route name in the reply and say where to look.
- Each option is a card showing its frames, the skill that argued for it, and what it costs. Put the recommendation first, with one line of reason.
- At least three options per surface. When skills disagree, give each skill's position its own option.
- Write the pick target to `docs/plans/mvp/PICKS.md` as `<surface> (<letter>): <option id>, <date>`. Downstream cards stay unstartable until their pick line exists.
- A motion option is a live sample on the same card list, not a prose spec alone. Put every motion option on one route with a switch, so Ivan can feel the difference. Replay the entrance by remounting the list under a key that changes with option, tab and run counter. Give each entrance animation a `prefers-reduced-motion` fallback. A scroll-driven option names its browser support in the UI and shows its content when unsupported.
- Before presenting motion, prove each option's animations run: `document.getAnimations()` names and durations per option, read in the Browser pane. A prose "no entrance animation" claim is unverified until those names match.
- Verify on the worktree's own :3100 server at desktop width, at 375 px (`document.documentElement.scrollWidth` must equal `innerWidth`), and in dark scheme. Read the console. Reset the tab afterwards per eventar-live-verify-worktree.
- Hand-back STATUS: `DONE (specimens), awaiting pick`. Do not mark the card done until the pick lands.
- Build every specimen from the real primitives in `components/ui` and the product's real classes and tokens. A look-alike re-typed from a product class string is not a specimen: it shows a design the product will not render. Before presenting, confirm each specimen imports the product component it stands for: grep each specimen file for its `components/ui` import. A file with no such import is a look-alike, and the round is not ready to present.
- Read contrast values only after every CSS transition has finished. In the Browser pane the animation clock can sit at 0, so `transition-all` Buttons report first-paint colours from `getComputedStyle`. Finish them first (`document.getAnimations().forEach(a => a instanceof CSSTransition && a.finish())`), then re-read. A probe that still prints "Measuring…" has no reading yet.
- A reviewer's contrast figure is a claim to re-measure, not a fact to put on a specimen. Re-measure in both schemes with transitions finished, cross-check against the token arithmetic in `app/globals.css`, and show the reviewer's figure beside the measured one. If they disagree because of the probe, withdraw the finding and say why.
- A specimen that stands in for a product overlay (modal scrim, drawer backdrop, menu surface) copies that class from the real primitive, not from memory. Grep it first (`grep -n -i -E "scrim|backdrop" components/ui/Dialog.tsx`); the 2026-10-25 UX-02 round guessed `bg-on-surface/40`, the primitive said `bg-on-surface/60`, and the specimen was corrected after the fact. Then check the overlay in dark scheme as well as light: a scrim that reads right on white can veil a dark page.
- A choice on a live product surface, where no specimen route fits, is rendered on the real page before the question. Copy the file to the scratchpad (`cp components/X.tsx <scratchpad>/X.orig.tsx`), apply each candidate, reload :3100 at 375 px and at desktop, send the frames with SendUserFile, restore the copy, and confirm `git status --short components/X.tsx` is clean. Only then ask with AskUserQuestion. Asking first with frames promised later is the violation.
- Every AskUserQuestion option carries its own render. The caption names what is simulated (stubbed search results, hidden dev overlays).
- Never apply a chosen option before Ivan picks it, and never pick for him.
- Push a pick-dependent frontend change only after its PICKS.md line exists, or after Ivan names that exact change. Approval of one row does not cover the other pending rows: list the pending rows again and ask for them. Commit with explicit paths and push a pinned SHA (`git push origin <sha>:main`), never a bare branch.
- Removal proposals (a QR, share block, link or card): before proposing, trace what the element targets. A QR or link that points at the page already open is circular; say so. Grep the shared helper's other callers (for example `lib/qr.ts` also feeds the organiser poster), so the removal touches only the page. Show before and after frames at 375 px and 1280 px, and name what disappears. Apply after the pick only: delete the element, its now-unused imports and its test mocks, then reload :3100 and re-render. Run tsc and eslint on the folder. Reset the viewport to `desktop`.
- After a pick lands, apply the token changes first, then re-measure. For each colour pair, compute WCAG contrast before and after in both schemes with a `javascript_tool` probe over `getComputedStyle`, and show the table in the reply. Match an ink to its container lightness, not to the old hex.
- A pick that changes a locked hex value (Frontend Design Standard §1, Q32) updates that doc in the same round. Otherwise the round is not closed.
- A typographic or CSS feature named in a pick (for example text-box trim) is kept only when the specimen shows a measured gain. Zero measured gain: drop it and say so in the reply.
- A stage-3 skill that conflicts with the locked Frontend Design Standard (for example `design-taste-frontend` on borders, gradients and shadows) is a conflict to surface, not a footnote. Give Ivan at least three options via AskUserQuestion, naming the skill that argued for each, per `~/.claude/CLAUDE.md`. Do not skip the skill and explain it in prose.
- A specimen that measures the DOM or tokens after mount trips `react-hooks/set-state-in-effect`. Silence it with one file-level `/* eslint-disable react-hooks/set-state-in-effect -- specimen: <why> */` line under `'use client';`. Insert that line with the Edit tool: `sed -i "1a\..."` fails on macOS.
- Align a specimen's columns by measurement, not by eye: after the edit and a reload, check that each element sharing a line has the same centreline and each element sharing a column the same left edge, then say so in the reply with the numbers. Use the `rendered-alignment-measurement` skill.
- A copy edit Ivan rejects (for example a register-card line he says he does not need) is reverted at once, not left for the next round. Confirm with `git diff -- <file>` that the file is empty before reporting the revert.
- While Ivan is iterating on a specimen's look, reload the route, show the changed frame, and stop. Run eslint, tsc, the 375 px sweep and the console read when he asks for them or says the frame is ready to commit. Launching them unasked mid-iteration got the run interrupted.
- Compressing a specimen card: fold a status into an existing row (the status pill sits beside the time, not on its own row), and keep the date cell a self-contained column. No full-width child may run across or under the date column. Measure card height before and after with `getBoundingClientRect` and report both numbers.
- The date cell is one fixed width on every card in the list, not sized to its content. Measure its `width` on all cards and report the spread (0 px means fixed). Selection tick boxes sit in a gutter outside the card, so they cannot push the date, the pill or the title.
- When Ivan names a paid or licensed component as the reference (for example "add the Card 4 block from React Bits Pro"), do not install it, enter a licence key, or copy its source. Follow its look and layout, write the code fresh from the project's own tokens and `components/ui` primitives, and present it as its own labelled option. If the licence blocks the source, say so in the reply and still build the fresh option.
- Before asking for a pick, re-check the round against the newest doctrine or IA doc in `docs/plans/` (any file dated after the round was built). If a doctrine changes the nav labels, the surface list or the home, the round is out of date: re-cut it under the doctrine first, or say in the reply that the picks describe a nav that will not ship. Do not present a stale round as ready.
- A pick can approve the recommendation and carve out an exception. Apply the option with that exception, record the exception on the PICKS.md line, and name it as a deviation. Do not turn it into a new option. Tables use an outer border only, not a full grid (Ivan, 2026-10-22).
- Before presenting a round, cross-check every "quiet call" or intro note against the option labels it describes. A note saying "the brand links to Registrations" beside option 5a linking to Events is a contradiction; grep the page for each named target after an edit.
- A before/after specimen pins the before to literal old values written into the file (the old px or rem numbers), never to a live product class. Once the product changes, a live class makes before and after identical and the diff disappears. The 2026-11-21 typography round showed this: "In the old specimen the headline \"before\" used the live class, which is now fluid, so before and after matched. The new page uses the fixed old sizes (hero 44px, headline-lg 39px) as \"before\"." Check that before and after differ in the measured values before publishing.
- When the old code is already gone, simulate the before frame: inject a style override into the pane (for example `:root{--text-hero:<old value>!important}`), read `getComputedStyle` on the element to confirm the value took, and caption the frame "simulated". A root-variable override can silently do nothing when a Tailwind utility reads the token through `@theme inline`; see eventar-frontend-type-radius-scale rule 15. Check the computed value, not the screenshot alone.
- After publishing an Artifact, exercise its controls in the Browser pane before sending the link: set each slider, click each toggle, read each readout. Name the controls exercised in the reply. If none were exercised, write "controls not exercised" instead of implying they work. Ivan, 2026-11-21 episode: "I loaded the page in the Browser pane but have not clicked through the controls or checked the readouts."
- Re-cutting a round: prepend a dated `## RE-CUT <date> (supersedes everything below it)` block to the card doc with the status, my picks, the checks and what was retired. Leave the older `STATUS:` line underneath, labelled superseded, so only one live status exists.

## Consistency sweeps: read, draft batches, apply on Ivan's word
1. Read every site the sweep names (file and line range). Quote its current classes. Never write a before from memory.
2. Draft one batch as rows: `Where | Before | After`. Mark a row that does not apply as dropped, with the reason.
3. Where two rules or skills disagree on a row, give at least three options, as in the pick process above.
4. Stop. Apply only the rows Ivan names ("Apply Batch N", or "Apply rows 1, 2, 7"). For a row he questions, render the after state on a scratch preview, measure it with `rendered-alignment-measurement`, and show the numbers. Change no product code for that row until he approves. Leave the batch uncommitted until he asks for a commit.
5. Apply with a cheaper model on disjoint file sets, giving each agent the exact class mapping and a Budget line.
6. Verify before reporting: `git diff --stat -- <paths>`; every changed line contains a mapped class and nothing else; the dead-class grep is clean; eslint passes on the changed files.
7. Report a batch as applied only after step 6. Name the rows left for the next batch.
