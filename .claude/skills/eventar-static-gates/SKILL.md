# Eventar static gates: run in order, reset only generated caches

Run the gates one at a time, in this order: `pnpm exec tsc --noEmit`, then `pnpm exec eslint .`, then `pnpm exec vitest run`, then `pnpm exec next build`. Heavy gates run sequentially. Never run `pnpm test:rls` alongside `next build`; contention fakes failures.
- `pnpm test:rls` runs in two stages (2026-11-02): a parallel stage, then a `--no-file-parallelism` stage. The serial stage holds the four files that run DDL in a transaction (`updateAsRoleWithGrant`) or hold registration row locks across transactions (`registration_contact_edit`, `event_soft_delete_privacy`, `registrations_link_immutability`, `registrations_insert_forgery`). Run in parallel, they deadlock. Put any new file that holds row locks across transactions in the serial stage. Do not gate such a test behind an env flag no script sets: that `skipIf` silently skipped the race test. Report `award_f1_f5_gate` null-fixture failures as a flake when they appear.

- Last recorded baseline (2026-10-16, with the organiser-timezone dashboard change, +1 test): vitest 1501 passed and 404 skipped (187 files passed, 46 skipped); eslint 1 pre-existing error in `app/settings/page.tsx` and 11 warnings; `next build` 39 routes. Expect the delta to match exactly what you changed.
- Gating a tip before push: run the gates in a detached worktree at that exact commit (`git worktree add --detach <scratch>/verify-<sha> <sha>`), not in the dirty checkout. Clone `node_modules` with `cp -Rc`. Pass the local-stack values as process env with the 127.0.0.1/localhost guard, keep `.env.local` empty for the run, and remove the worktree afterwards. Before the run, take `scratch-demo/locks/test-rls.lock`: refuse if it already exists, otherwise write your session and SHA into it. Remove the lock and the worktree in an EXIT trap so a failing step cannot leave the lock behind. Last run on main tip 9cb0de2 (2026-10-16, pushed): tsc exit 0; vitest 1531 passed and 404 skipped (187 files passed, 46 skipped); next build 39 routes. Those counts supersede the vitest line above for main from that tip on. Last green tip gate on `1d03e3b` (2026-10-25, DB-05, RLS suite included): tsc exit 0; eslint 0 errors and 11 warnings; vitest 258 files and 2380 tests passed; next build exit 0. Compare RLS-inclusive runs against this line, not the 2026-10-16 counts.
- A test that passes alone but fails in the full run under peer load: check `uptime` first (load was 29 with three peer sessions), then rerun the full suite with `--maxWorkers=4`. Report the first failure as a flake, never as a pass.
- A test green before some hour and red after it is a clock assertion, not a flake. Do not rerun it; pin the clock per the global `time-dependent-test-fixed-clock` skill.
- `Test timed out in 5000ms` in files your change did not touch is the same flake. Rerun those files alone (`pnpm exec vitest run <file> ...`) and report the isolated result. On 2026-10-15 three such files failed in the full run and passed 78/78 alone.
- Before commit, scan added copy lines for the em-dash (Decisions Log Q41: no em-dashes in new copy): `git diff -U0 -- app components lib | grep -E '^\+[^/*].*—'`. Use `grep`, not `rg`: `rg` is not on the gate shell's PATH (exit 127), so the scan silently did not run on 2026-10-31 and 11-01. Fix any hit that is new copy. A hit on a line you only reshaped (an existing label rewritten around a variable) is pre-existing copy: report it, do not silently rewrite it.
- `next build` regenerates `.next/types`. If tsc then fails on stale generated types, check that no dev server is running (`lsof -nP -iTCP -sTCP:LISTEN`), delete only `.next/dev/types`, and re-run tsc. Never delete source to make a gate pass.
- A tsc run that hangs at low CPU or exits 134 (OOM) after a type change is usually a stale incremental cache, not the change. Reproduce from HEAD: check out the HEAD versions of the changed files in a clean extract (no `.next`), run `tsc`, then restore your files and re-run incrementally with that buildinfo. Deleting `tsconfig.tsbuildinfo` or `.next/cache/.tsbuildinfo` only hides the hang on this checkout; every other checkout hits it on its next incremental build.
- Exported generics that wrap supabase-js `.select(cols)` (e.g. `ownEvents`) OOM incremental tsc when the row type is left inferred. Spell the second select generic out (see `eventar-org-scoped-event-lists`).
- `vitest run` skips the RLS files unless `RLS_TESTS=1` is set, and still reports a pass. Before reporting the vitest gate, check the skipped count against the RLS-inclusive baseline line above. On 2026-10-25 a run without the flag gave 1849 passed and 544 skipped; the same tree with `RLS_TESTS=1` gave 258 files and 2393 tests, all passed. Re-run with the flag set; never report the unflagged count.
- Read the real exit code. Piping hides it in zsh. Use `${pipestatus[1]}` or run the command unpiped first.
- A gate wrapper that pipes a test run through `tail`, `head` or `sed -n` can print `exit=1` with no failing names. Before reporting a failure, rerun that gate with full output written to a file, list each failure with `grep -E '^ FAIL '`, and check failed + passed = total (`Tests  16 failed | 2377 passed (2393)`). On 2026-10-31 the first tip-gate run showed only `exit=1` for the auth paths; the untruncated run named 16 failures, all in `app/login/page.test.tsx` and `app/account/sign-in/page.test.tsx`.
- macOS zsh has no `timeout` binary. `timeout 170 pnpm exec vitest run ...` fails at once with `(eval):1: command not found: timeout` and runs no tests. Drop the wrapper and bound the call with the Bash tool's `timeout` parameter, or run the chain in the background (see the sentinel bullet below).
- After you move a file between `pnpm test:rls` stages, or add one, prove each RLS file runs in exactly one stage: list both stages with `vitest list --filesOnly` and check for overlap and gaps against the RLS file set. A file in neither stage is silently skipped; a file in both runs twice.
- The tree and the local Supabase stack are shared with peer sessions.
- Two extra gates sit beyond the four above: `pnpm check:ui-colours` and `pnpm check:ui-primitives`. On 2026-10-22 both failed, reporting `components/dashboard/DashboardWorkstation.tsx`, `app/settings/OrgOnboardingClient.tsx` and `app/events/[id]/checkin/RosterClient.tsx`, which the card did not touch [I, not yet diffed against HEAD]. Before editing, save each gate's output to the session scratchpad as the baseline. Report "unchanged" only after diffing the failing list against that file.
- On 2026-10-24 both still failed. To prove a violation predates your diff, run `git show HEAD:<file> | grep -n '<pattern>'` and match the line text. Compare by text, not line number: the hero-gradient `rgba(` moved from line 218 to 202 when unrelated code above it changed. A violation present at HEAD is pre-existing. Report it as pre-existing and do not fix it inside a card that does not own it.
- `app/events/[id]/edit/PublishDraftButton.test.tsx` (the path moved from `components/details/`) failed in 1 of 3 full `vitest run` passes on 2026-10-22, and in 1 of 1 full tip-gate run on 2026-10-23 (test "when the draft is no longer current, says so, links Manage, offers only Close, and refreshes the page when closed"). Both times it passed alone; on 2026-10-23 five isolated reruns passed 12 of 12 each. Treat it under the flake rule above: report the first failure as a flake, with the isolated rerun. On 2026-10-24 the CX-04 tip-gate vitest run failed in `PublishDraftButton` and `MagicLinkSignInForm`. Rerun each alone before reporting it as a flake, and record the isolated result.
- Full `vitest run` needs Supabase env. `tests/helpers/env.ts` throws if `.env.local` is missing, and gated files build a Supabase client at import, so an empty file alone still fails 46 files with "supabaseUrl is required". Pass the local-stack values as process env from `supabase status -o env` (API_URL, ANON_KEY, SERVICE_ROLE_KEY, mapped to NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY), refuse unless API_URL is 127.0.0.1 or localhost, and create an empty `.env.local` only for the run. Delete it after. Never copy values from `.env.local`. Before blaming a failing gate on your change, check the other sessions and their running servers.
- `next build` in a detached worktree fails with exit 1 when `node_modules` is a symlink: Turbopack reports `Symlink [project]/node_modules is invalid, it points out of the filesystem root`. Clone it with `cp -Rc`, never symlink it. If the build still cannot run there, report the tooling failure and name the checkout that passed; do not call the build green from the failed run.
- A full gate chain (tsc, eslint, vitest, next build) takes about two minutes, past what one foreground tool call should block on. Run the chain in the background into a file that ends with a sentinel (`(zsh gate.sh > gate.out 2>&1 &)`, script ends with `echo "== done"`), then poll with a bounded loop: `for i in $(seq 1 100); do grep -q "^== done" gate.out && break; sleep 6; done`. Read each `== <gate>` section and its exit line. Never report a gate as passed from the sentinel alone.
- Local stack down (Docker not running, `supabase status` fails): do not substitute placeholder URLs or keys to get the gate green. Start the stack first, or run tsc, eslint, vitest and build with the RLS suite marked NOT RUN, and report the skipped count beside the pass count. On 2026-10-31 a merged-tree run with placeholder env gave 1855 passed and 544 skipped; that proves compile, lint and build, not database behaviour.
- Gating a branch against a moved main before push: check conflicts with `git merge-tree --write-tree main <branch>`, then gate the merged result without moving any ref. Make an unreferenced merge commit with `git commit-tree <merged-tree> -p main -p <branch>`, check it out detached, run the chain, and remove the worktree and lock in the EXIT trap. Never name that commit in a handoff as the branch tip.
- Review fixes reopen the gates. After any dev-lens or user-lens fix lands, re-run the full chain (tsc, eslint, vitest with `RLS_TESTS=1` when the RLS suite is in scope, then `next build`) before the phase is presented. A subset run such as `vitest run app/account components/shell` is a spot check; if it is all you ran, say that in the report, never "gates green".
- A gate count written in a handoff is a claim, not a baseline. On 2026-11-01 the MVP review reported `check:ui-primitives` with 4 hits where the handoff said 3; all 4 predated the base commit (raw buttons counted with `git show BASE:file | grep -c`, and the script's last change checked by commit). Run both check scripts, quote the live count, and label which hits predate the base.
