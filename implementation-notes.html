Phase 2 — Registration flow — Implementation notes

Started 2026-05-20 · Live document, updated as implementation progresses · Implementation complete; awaiting manual smoke

This file captures decisions, deviations, tradeoffs, and open questions for the Phase 2 implementation. The spec is the inline registration form on /events/[id] with two new tables (registrations + email_log), a Server Action that inserts the email_log row first per CLAUDE.md rule 5, and stub-logging until Phase 7 wires Resend. Full design discussion lived in the conversation that preceded this file.

Design decisions live

D1 Shipping the BASE spec, not the 4-option superset

Before implementation, four shape options were discussed: (A) base spec, (B) add visible capacity counter, (C) add affiliation field, (D) wrap whole flow in a single RPC for atomicity. The user said "implement <SPEC>" — interpreted as option A only. B / C / D are recorded as open questions below; implementing them later is straightforward.

D2 Multi-step Server Action over a single RPC

Considered: one PG function (register_for_event) that locks the event row, inserts email_log, inserts registrations, and updates email_log atomically. Rejected for now because: (a) the email_log-first ordering is the explicit hard rule from CLAUDE.md and is easier to reason about as separate, traced steps; (b) Phase 7 will wire Resend between the queue insert and the status update, and that split is cleaner outside a single PG function; (c) we already have supabaseAdmin for the email_log insert (service-role, bypasses RLS); the anon client handles registrations under RLS. Race condition (two registrants under capacity simultaneously pushing total over capacity) is acknowledged and accepted for MVP scale — see Q1.

D3 Email_log row is service-role-only

No RLS policy gives anon or authenticated users access to email_log. The Server Action uses supabaseAdmin() (service-role) for inserts and updates. This keeps the ledger as a server-only operational concern; client code never reads it. Future analytics (Phase 6) and cron sender (Phase 9) will also use service-role.

D4 Field set is minimum-viable

Just full_name and email on the registration form. PRD §5 doesn't specify additional fields. Affiliation, phone, dietary preferences, etc. all deferred. The registrations table is open to add columns later without breaking the unique constraint (which is on (event_id, email)).

D5 Status enum: registered, attended, cancelled

Only registered (default) is used in Phase 2. attended is set in Phase 4 (check-in). cancelled is for user-self-cancel; no UI in Phase 2, but the value is in the enum to avoid a migration later.

Deviations live

V1 Zod 4 z.string().uuid() is v4-strict

My first test fixture used 00000000-0000-0000-0000-000000000001 as the event_id — looks like a UUID, isn't a v4. Zod 4's z.string().uuid() rejects anything that doesn't have 4 as the first digit of the third group and 8|9|a|b as the first digit of the fourth. Three test failures surfaced this in 30 seconds. The schema is correct (Postgres gen_random_uuid() always produces v4, so the strict check matches reality). Fixed the fixture, not the schema. Worth flagging as a Zod-4 gotcha for future tests.

V3 Server Action also needs admin for the insert + capacity count caught by live-DB backtest

First-pass review missed two bugs that the live-DB backtest surfaced immediately:

  1. Capacity count silently returned 0. Step 3 of the Server Action did anon.from('registrations').select('id', { count: 'exact', head: true }). Anon has no SELECT policy on registrations (PII), so the count was always 0 — capacity gate never fired and users could register past max_attendees. Same bug class as V2 on the public page, just one function deeper.
  2. Anon insert with RETURNING failed every time. Step 5 did anon.from('registrations').insert(...).select('id').single(). The .select() compiles to PostgreSQL's RETURNING clause, which requires SELECT privilege on the inserted row. Anon has none. Error message "new row violates row-level security policy for table registrations" was misleading; the WITH CHECK passed (subquery confirmed event is published), but the SELECT-for-RETURNING phase was denied.
    The live backtest table-test isolated this by running insert with and without RETURNING as anon: without succeeded, with failed.

Fix for both: use supabaseAdmin() for the count and insert in the Server Action. The anon RLS policy stays unchanged — it's still the defense-in-depth guarantee against direct REST API hits to /rest/v1/registrations. The Server Action's step 2 explicit event.status === 'published' check is the primary gate for our own code path.

V2 Public-page registration count uses supabaseAdmin()

Initially wrote the count query against the anon client and only caught the issue on the re-read: anon has no SELECT policy on registrations (PII), so the count would have come back null and the at-capacity check would never fire. Switched to supabaseAdmin() just for the count. The count itself is a non-sensitive integer; surfacing it on the public page is safe. The row PII is still locked behind the organizer/manager policies.

Alternative considered: add an RLS policy allowing anon to count but not read registration rows. Postgres RLS doesn't have a way to distinguish COUNT(*) from SELECT — the policy applies row-by-row, so an anon-allow policy would also expose row data. The two cleaner alternatives are (a) supabaseAdmin() for the count (what we shipped — minimal, server-only), or (b) a security definer SQL function public.event_registration_count(uuid) exposed to anon. (b) is more idiomatic but heavier; we'll migrate to it if Phase 6 analytics push more aggregate-style queries through this path.

V3 Server Action uses supabaseAdmin() for the registrations INSERT too

Same class of bug as V2, caught during the live-DB backtest. The Server Action originally did insert(...).select('id').single() through the anon client. The anon RLS policy grants INSERT (when event is published) but not SELECT. Postgres's RETURNING clause — which Supabase's .select() after insert triggers — requires SELECT on the new row. Anon-INSERT-with-RETURNING fails with the misleading "new row violates row-level security policy". Verified by hitting the same shape directly via set local role anon — confirmed via backtest A4 that pure anon INSERT without a returning works, while the JS client's default insert pattern doesn't.

Two ways to fix: (a) add an anon SELECT policy gated to "newly-inserted-row only" via a returning policy — Postgres doesn't really support this cleanly; (b) use the service-role for the insert. Picked (b). The defense-in-depth value of the anon-INSERT RLS policy is preserved for any direct hits at /rest/v1/registrations (where the client doesn't need RETURNING). The Server Action's own flow already verified event.status = 'published' in step 2 before the insert, so bypassing RLS for this specific call is safe.

Code comment in actions.ts lines 99–107 documents this in-place so the next reader doesn't have to retrace.

Tradeoffs live

T1 Capacity race condition: accept it

Two anon visitors registering simultaneously could both pass the count(*) < max_attendees check and both insert, ending up at max_attendees + 1 total. Alternative: row-level lock the event row via SELECT ... FOR UPDATE inside an RPC. Rejected: (a) Eventar's PRD targets ≤200 attendees/event with low concurrent-registration intensity (workshops, not flash sales); (b) we can add a trigger-based hard cap later if it bites in practice; (c) keeping the flow as a multi-step Server Action without an RPC keeps debugging simple in Phases 2–6.

T2 Stub log instead of real email

Per CLAUDE.md hard rule 7 ("Don't add external services prematurely. Resend wired in phase 7") and the vault's Phased Roadmap ("entire MVP runs locally with no external service"), Phase 2 only does console.log('[email stub] would send confirmation to X'). The email_log row still goes in first, so when Resend lands the order is already right and we can replay queued rows.

Open questions live

Q1 Should we add the visible capacity counter? open

Spec option B from the design conversation. Adds one read query to the page and one display line ("12 of 50 spots remaining"). Defer unless the manual smoke shows the form's "at capacity" message feels confusing after the fact. Cost to add later: 15 minutes.

Q2 Should we add an affiliation field? open

Useful for Phase 6 analytics (who's coming from where?). Adds one column + one form field. Decision: defer to first user complaint that the registration data is too thin. Migration to add the column later is one ALTER TABLE.

Q3 Should organizer view of registrations land in Phase 2 or Phase 6? open

Phase 2 demo per the roadmap shows the anon-side flow only. But adding a basic "Registrations (N)" count to /events/[id]/edit would let the organizer verify their event is working without inspecting the DB. Cost: 20 minutes. Decision: defer to Phase 6, but mention in the manual smoke handoff that the organizer can verify via select count(*) from registrations in SQL editor.

Manual smoke checklist awaiting user

The dev server (your pnpm dev on :3000) hot-reloaded the new code. As an authenticated staff user, walk through this in order:

  1. Create a draft event with max_attendees=2 (so the at-capacity state is reachable). Publish it. Note the event id.
  2. Open /events/{id} in incognito. Confirm the page renders with venue, agenda, and a "Register for this event" card at the bottom.
  3. Fill in a name + your email → click Register. Expect the form to swap to the green "✓ You're registered!" card. Server log should show [email stub] would send confirmation to {email} for event "{title}" (registration {uuid}).
  4. Reload /events/{id} in the same incognito session. Form is back (fresh page render). Try to register the same email again. Expect the red banner "You're already registered for this event."
  5. Open a second incognito window. Register a different email. Now the event is at 2/2.
  6. Reload /events/{id}. Expect the at-capacity card: "This event is at capacity (2/2 registered)…" instead of the form.
  7. In Supabase SQL editor, run select email, full_name, status from registrations where event_id = '{id}'; — expect 2 rows with the two test emails (lowercased). Then select purpose, recipient_email, status from email_log where event_id = '{id}'; — expect 2 rows, both status='sent'.
  8. Create a draft event (don't publish) → try /events/{drafted_id} in incognito. Expect 404 (page is anon-gated by RLS + status check).

Report any deviations from these expected outcomes here for follow-up.
