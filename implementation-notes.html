Phase 2 — Registration flow — Implementation notes

Started 2026-05-20 · Live document, updated as implementation progresses · In progress

This file captures decisions, deviations, tradeoffs, and open questions for the Phase 2 implementation. The spec is the inline registration form on /events/[id] with two new tables (registrations + email_log), a Server Action that inserts the email_log row first per CLAUDE.md rule 5, and stub-logging until Phase 7 wires Resend. Full design discussion lived in the conversation that preceded this file.

Design decisions live

D1 Shipping the BASE spec, not the 4-option superset

Before implementation, four shape options were discussed: (A) base spec, (B) add visible capacity counter, (C) add affiliation field, (D) wrap whole flow in a single RPC for atomicity. The user said "implement <SPEC>" — interpreted as option A only. B / C / D are recorded as open questions below; implementing them later is straightforward.

D2 Multi-step Server Action over a single RPC

Considered: one PG function (register_for_event) that locks the event row, inserts email_log, inserts registrations, and updates email_log atomically. Rejected for now because: (a) the email_log-first ordering is the explicit hard rule from CLAUDE.md and is easier to reason about as separate, traced steps; (b) Phase 7 will wire Resend between the queue insert and the status update, and that split is cleaner outside a single PG function; (c) we already have supabaseAdmin for the email_log insert (service-role, bypasses RLS); the anon client handles registrations under RLS. Race condition (two registrants under capacity simultaneously pushing total over capacity) is acknowledged and accepted for MVP scale — see Q1.

D3 Email_log row is service-role-only

No RLS policy gives anon or authenticated users access to email_log. The Server Action uses supabaseAdmin() (service-role) for inserts and updates. This keeps the ledger as a server-only operational concern; client code never reads it. Future analytics (Phase 6) and cron sender (Phase 9) will also use service-role.

D4 Field set is minimum-viable

Just full_name and email on the registration form. PRD §5 doesn't specify additional fields. Affiliation, phone, dietary preferences, etc. all deferred. The registrations table is open to add columns later without breaking the unique constraint (which is on (event_id, email)).

D5 Status enum: registered, attended, cancelled

Only registered (default) is used in Phase 2. attended is set in Phase 4 (check-in). cancelled is for user-self-cancel; no UI in Phase 2, but the value is in the enum to avoid a migration later.

Tradeoffs live

T1 Capacity race condition: accept it

Two anon visitors registering simultaneously could both pass the count(*) < max_attendees check and both insert, ending up at max_attendees + 1 total. Alternative: row-level lock the event row via SELECT ... FOR UPDATE inside an RPC. Rejected: (a) Eventar's PRD targets ≤200 attendees/event with low concurrent-registration intensity (workshops, not flash sales); (b) we can add a trigger-based hard cap later if it bites in practice; (c) keeping the flow as a multi-step Server Action without an RPC keeps debugging simple in Phases 2–6.

T2 Stub log instead of real email

Per CLAUDE.md hard rule 7 ("Don't add external services prematurely. Resend wired in phase 7") and the vault's Phased Roadmap ("entire MVP runs locally with no external service"), Phase 2 only does console.log('[email stub] would send confirmation to X'). The email_log row still goes in first, so when Resend lands the order is already right and we can replay queued rows.

Open questions live

Q1 Should we add the visible capacity counter? open

Spec option B from the design conversation. Adds one read query to the page and one display line ("12 of 50 spots remaining"). Defer unless the manual smoke shows the form's "at capacity" message feels confusing after the fact. Cost to add later: 15 minutes.

Q2 Should we add an affiliation field? open

Useful for Phase 6 analytics (who's coming from where?). Adds one column + one form field. Decision: defer to first user complaint that the registration data is too thin. Migration to add the column later is one ALTER TABLE.

Q3 Should organizer view of registrations land in Phase 2 or Phase 6? open

Phase 2 demo per the roadmap shows the anon-side flow only. But adding a basic "Registrations (N)" count to /events/[id]/edit would let the organizer verify their event is working without inspecting the DB. Cost: 20 minutes. Decision: defer to Phase 6, but mention in the manual smoke handoff that the organizer can verify via select count(*) from registrations in SQL editor.
