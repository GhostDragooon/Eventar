## Goal / demo end-state

A staff member opens `/dashboard` and sees:

- **Top "General Category" band — 4 tiles**: Days Until Next Event · Events by Status (5 mini-counts) · Aggregate Registration (across Registering + Upcoming) · Team Task Completion (logged-in user's own % completed).
- **Event list grouped by lifecycle stage** in chronological progression: Drafted → Registering → Upcoming → Live → Completed. Completed section collapsed by default. Each slice carries name · date · `X/Y` registration · status pill, with status-aware click destinations.

Clicking a slice routes to the most useful surface for that lifecycle:

| Stage | Destination | Why |
|---|---|---|
| Drafted | `/events/[id]/edit` | continue editing |
| Registering | `/events/[id]/details` (NEW) | operational/funnel surface |
| Upcoming | `/events/[id]/details` | same |
| Live | `/events/[id]/checkin` | live roster, most actionable surface during event |
| Completed | `/events/[id]/analytics` | survey deep-dive (Phase 6 page, unchanged) |

The new `/events/[id]/details` surface is a **lifecycle dashboard** with three real sections: Registration · Attendance · Feedback. Each section renders unconditionally with lifecycle-aware empty states.

No new tables. One new nullable column (`registration_close_at`). No new dependencies. Read-only queries via `supabaseServer`, matching the Phase 6 (Q16 Decision C) architectural pattern.

## Lifecycle state machine

Pure function in `lib/lifecycle/eventLifecycle.ts`:

```ts
export type Lifecycle = 'drafted' | 'registering' | 'upcoming' | 'live' | 'completed';

export function computeLifecycle(
  event: {
    status: 'draft' | 'published' | 'completed' | 'cancelled';
    start_time: string;
    end_time: string;
    registration_close_at: string | null;
  },
  nowMs: number,
): Lifecycle | 'cancelled' {
  if (event.status === 'cancelled') return 'cancelled';
  if (event.status === 'draft') return 'drafted';
  if (event.status === 'completed') return 'completed';

  // status === 'published' branch
  const startMs = new Date(event.start_time).getTime();
  const endMs = new Date(event.end_time).getTime();
  const closeMs = event.registration_close_at
    ? new Date(event.registration_close_at).getTime()
    : null;
  const autoCompleteMs = endMs + 48 * 60 * 60 * 1000;

  if (nowMs >= autoCompleteMs) return 'completed';
  if (nowMs >= startMs && nowMs <= endMs) return 'live';
  if (nowMs > endMs) return 'completed'; // gap between end_time and +48h still reads as completed for UI; cron will eventually flip
  // nowMs < startMs branch
  if (closeMs != null && nowMs >= closeMs) return 'upcoming';
  return 'registering';
}
```

**Test plan** (TDD, written first):
1. status='cancelled' → 'cancelled' regardless of timestamps
2. status='draft' → 'drafted'
3. status='completed' → 'completed'
4. published + before start + no close set → 'registering'
5. published + before start + close in past → 'upcoming'
6. published + close in future → 'registering' (boundary check)
7. published + during event window → 'live' (start boundary inclusive)
8. published + during event window → 'live' (end boundary inclusive)
9. published + after end + within 48h → 'completed' (derived auto-complete)
10. published + after end + beyond 48h → 'completed' (the same outcome; both paths covered)

Helper consumed by: `/dashboard` (slice grouping + General Category counts), `/details` header pill + Section visibility, edit page status badge.

### Motion

Per the frontend-design skill: *"Match implementation complexity to the aesthetic vision."* Eventar's vision is refined-utilitarian for internal staff — motion serves clarity, not delight. Two motion uses in this phase:

1. **Live pill background pulse** — custom keyframe `livePillBgPulse` that animates only the `background-color` between full M3 error red (`rgb(186 26 26)`) and the same red at 55% alpha (`rgb(186 26 26 / 0.55)`) over a 1.8s ease-in-out cycle. Applied via a `.live-pill-pulse` class. **The dot and the text do not pulse** — only the pill background does. Rationale: Tailwind's built-in `animate-pulse` animates opacity on the whole element, which fades the text and reduces legibility. Pulsing background-color preserves crispness while still carrying the "happening now" signal.

   Keyframe to add to `app/globals.css`:
   ```css
   @keyframes livePillBgPulse {
     0%, 100% { background-color: rgb(from var(--error) r g b); }
     50%      { background-color: rgb(from var(--error) r g b / 0.55); }
   }
   .live-pill-pulse { animation: livePillBgPulse 1.8s ease-in-out infinite; }
   ```
   (`rgb(from … r g b)` is a CSS Color Module 5 relative-color syntax — supported in all evergreen browsers. If we hit an older-browser regression we can hardcode the hex.)

2. **Hover transitions** — `transition-colors` on slices and buttons, matching the existing `hover:bg-surface-container-low` pattern. No `transition-all`.

**Explicitly skipped**: staggered page-load reveals, scroll-triggered animations, parallax, gradient meshes, noise textures. These are appropriate for marketing surfaces; this is an internal ops dashboard. The frontend-design skill's "bold maximalist" framing is the inverse of what fits here — restraint IS the design statement.

## Open items / known constraints

- **Auto-completion derived in UI, not in DB.** When Phase 9 (pg_cron) lands, replace the derivation with a scheduled `UPDATE events SET status='completed' WHERE status='published' AND end_time + interval '48 hours' < now()`. The lifecycle helper continues to work — it just collapses to a pass-through for status='completed' rows.
