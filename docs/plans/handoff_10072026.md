## The pattern that mattered most this sprint: per-task review kept finding real bugs in the plan's own literal SQL

Every single table/function task (3 through 9) had at least one genuine defect caught by spec-compliance or code-quality review — not implementer typos, but real gaps in the plan document itself, several with live-regression or security consequences:

1. **Task 2** — the plan's own "pinned fact" about `staff.role`'s existing values was wrong (said 2, live was different), and the widen itself broke 3 already-shipped `SECURITY DEFINER` functions (`transition_dsr`/`mark_attended`/`publish_event`) whose role-gate literals became permanently dead. Worse, code review then found `app_private.is_manager()` and `pseudonymise_user` had the *same* bug, but as a **live regression** — the sole staff account had already silently lost cross-owner RLS read access to events/registrations/etc. the moment the migration applied. Backtested the fix with a simulated JWT session before moving on.
2. **Task 5** — the plan's `practitioner_licences_self_write` policy would have let a practitioner directly set `status='verified'` on their own row via a plain client write, completely bypassing Task 6's staff-verification functions (which are `SECURITY DEFINER` and bypass RLS by design — they'd have added a second *safe* path without closing the first *unsafe* one). Dropped the policy before Task 6 even started.
3. **Task 6** — `supersede_licence` had no from-state guard, letting a practitioner self-supersede a `revoked` licence and route around a staff disciplinary action. Ivan's call: block superseding `revoked`/`superseded`, allow `declared`/`verified`/`lapsed` (the last is a legitimate renewal path).
4. **Task 8** — the plan's hash design had a real collision bug (`points`/`hours` concatenated with no delimiter — `(1,1)` and `(11,NULL)` hashed identically) and covered only 6 of ~15 semantic columns, meaning most of a credit entry was silently mutable with `verify_ledger_chain()` still reporting valid. Both fixed with `jsonb_build_object` (field-boundary-safe, covers every column) plus pinned session GUCs, while the ledger was still empty — the only cheap moment to fix an append-only chain's hash design.
5. **Task 8** (same review) — the append-only posture was enforced at the RLS-policy level but never at the table-grant level; `service_role` (which bypasses RLS entirely) could still write directly. Fixed with an explicit table-level revoke, mirrored from `audit_events`.
6. **Task 10 exit gate, dev-lens review** — found the *exact same* table-grant gap on `practitioner_licences` that Task 8 had just closed on `credit_ledger`. The six Task 6 functions had never actually been the sole mutation path for `service_role`.
7. **Task 10 exit gate, user-lens review** — caught something the dev-lens fix itself broke: revoking `practitioner_licences`' grants also broke this sprint's own committed test fixtures (16/34 tests), which had been creating rows via direct admin insert rather than the RPCs. Surfaced a genuine design question along the way (should `practitioner_licences` be delete-locked like `credit_ledger`, or does it need a cleanup path?) — Ivan's call: re-grant `DELETE` only, since it isn't a permanent financial ledger the way `credit_ledger` is and has no ephemeral-branch testing option on this Supabase plan.

**Takeaway for whoever plans Sprint 3b's SQL-heavy tasks:** treat this plan document's literal SQL as a draft, not ground truth, the same way Sprint 3a's own plan turned out to need. Budget real review time per task, not just implementation time — on this sprint, review found more genuine defects than implementation introduced.

## Two things worth flagging that aren't bugs, just decisions made along the way

1. **Branching isn't available on this Supabase project's plan.** The original design called for Task 9's concurrency/chain-integrity test to run on an ephemeral Supabase branch (to avoid ever writing synthetic data into the regulator-facing `credit_ledger`). `create_branch` returned `PaymentRequiredException: Branching is supported only on the Pro plan or above`. Fell back to a direct backtest against the live project with rigorous insert-verify-cleanup discipline instead — worked, but means `credit_ledger`'s hash chain has zero automated *test* coverage (verified manually, multiple times, by multiple review passes, but nothing runs in CI). If branching becomes available (plan upgrade) or Sprint 3b wires a real caller (real rows accrue naturally), this is the moment to add the committed test.
2. **The `credit_dispute` → `credit_disputes` rename.** Every other entity table in this schema is plural; `credit_dispute` wasn't, and it was free to fix while the table had 0 rows and nothing referenced it. Constraint/index names under the old singular survived the rename (cosmetic only — logged in DEFERRED.md, not worth another migration).
