## Critical bug found and fixed during phase-completion review

Two independent review agents (dev-perspective + user-perspective, run separately per the phase-completion protocol) both converged on the same finding: **`specialties` is seeded for `medicine` only.** Every other profession (12 of 13) hit a permanent dead end — empty dropdown, no reachable free-text fallback (the escape hatch only appeared when `specialty_code === 'other'`, which doesn't exist as an option when the list is empty), Continue permanently disabled. This would have made account creation impossible for any non-medicine practitioner.

Fixed in both `CompleteClient.tsx` and `ProfileClient.tsx`: the free-text field now also renders whenever the filtered specialty list is empty for the selected profession, with the picker itself disabled and re-labelled ("Not listed yet — use the field below") rather than left as a dead, confusing dropdown.

Fixing this surfaced a second bug: `f3Ready` (ProfileClient) and `profileReady` (AccountClient, via `app/account/page.tsx`) predated the F3 widening above and never checked specialty — both would have shown a green "complete" readiness banner for a profile that would actually fail credit release at check-in. Fixed both; added a dedicated regression test for each (`ProfileClient.test.tsx`, plus the SQL-level `award_f1_f5_gate.rls.test.ts` fixture).

Verified live end-to-end, not just by test: signed up a fresh nurse (no seeded specialties for her profession) through all 4 real wizard steps against the local stack, confirmed via direct SQL that `professional_profiles.specialty_other = "Cardiac Nursing"`, the licence, and both consent rows landed correctly, and that `/account` rendered full green readiness afterward.

## Findings investigated and ruled out (not real bugs)

Both review agents' live-testing windows overlapped with active file edits (Turbopack hot-reload), and a few reported findings didn't reproduce against the settled code:

- **`ReferenceError: filteredSpecialtiesForForm is not defined` crash on `/account/profile`** — variable is correctly declared in-scope (`grep` + `tsc --noEmit` both confirm); reproduced the exact add/remove appointment and society interactions cleanly with zero console errors. Very likely a transient half-applied-HMR-state crash caught mid-edit, not a persistent defect.
- **"Declaring a licence auto-completes the flow, skipping Done"** — investigated at length (isolated clicks, network logs, dev-server logs). Confirmed real in two live runs but couldn't pin a code-level cause: no `router.push` exists outside the `Done` button's own handler. Data integrity is unaffected either way (verified via direct SQL both times) and the landing page is the same one `Done` would produce — flagged as unresolved rather than either buried or given a confident wrong cause. Worth a closer look if it recurs.

- **`review-animations`** (locked pipeline stage 5b) has `disable-model-invocation: true` — could not self-invoke. Available via `/review-animations` if a stricter animation-craft pass on the new wizard is wanted.
