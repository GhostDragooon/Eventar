## 2. Real event evidence settles the multi-body-per-event question

Ivan attached two PDFs for a real, currently-scheduled event: **Innovative Cardiovascular Initiative Summit 2026**, 8–9 August 2026, Charles K. Kao Auditorium, Science Park HK.

The accreditation sheet shows **one event accredited by 13 bodies simultaneously**: 11 HKAM Colleges (Anaesthesiologists, Community Medicine, Emergency Medicine, Family Physicians, O&G, Otorhinolaryngologists, Paediatricians, Pathologists, Physicians, Radiologists, Surgeons) + MCHK + **CNE (Continuing Nursing Education — not a medical body at all)**. Each body awards a **different point value**, and that value further splits by **Day 1 / Day 2 / Both Days independently per body** — e.g. Pathologists: 11/5/6, CNE: 10.5/5/5.5, Anaesthesiologists: 10/4.5/5.5.

**Conclusion, not a hypothesis:** `events.accrediting_body_id` (a single scalar UUID) cannot represent this event at all. Multi-body-per-event is real, needed now, and includes a day-scoping dimension the earlier framing hadn't accounted for. This was the open decision item #2 from `handoff_14082026_v2.md` §5 — now resolved: **in scope, not Stage 13+.**

## 4. Multi-body accreditation — the design, read-only investigation only

**Read, not written:** `award_attendance_credit`'s current full body (single-body lookup: reads `events.accrediting_body_id`/`cpd_hours`, checks one licence, posts one `credit_ledger` row), `record_credit_entry`'s full parameter list (14 params, already generic — `p_body_id`, `p_points`, `p_hours`, `p_category` all already exist as separate columns, nothing here blocks multi-body), the `credit_ledger` schema, the `credit_ledger_attendance_uniq` partial unique index (`(user_id, event_id) where entry_type='credit_earned'` — **this specifically blocks a practitioner earning more than one attendance credit for the same event**, which multi-body awarding needs to legitimately do when someone holds licences at 2+ of the event's accrediting bodies; this index needs to become `(user_id, event_id, body_id)` as part of the change), and all three call sites (`app/events/[id]/checkin/actions.ts`, `app/events/new/actions.ts`, `lib/cpd/awardAttendanceCredit.ts`).

**Proposed shape, not yet built:**
- New table `event_accreditations`: `event_id`, `body_id`, `applies_from`/`applies_to` (timestamptz range — not a hardcoded "day1/day2" enum, so it handles events of any length and matches the genericity directive already locked for Task 10.3), `credit_value numeric`, `unit text`. One event, many rows — one per (body, day-scope) combination on the poster.
- `award_attendance_credit` reworked to iterate every accreditation row for the event, check the practitioner's licence against each body independently, match their attendance window against each row's date range, and post **one `credit_ledger` row per body they hold a verified licence at** — not one row total. This is the "one evidence record, many authority-specific claims" thesis from the strategy doc, now with a real forcing example instead of a hypothetical.
- `credit_ledger_attendance_uniq` widens to include `body_id`, for the reason above.
- `events.accrediting_body_id`/`cpd_hours` (Task 10.1's shipped, live, tested columns) stay as-is — additive change, not a breaking replacement of what's already in production.
- This reshapes Task 10.3–10.5, not just adds a task; the plan file's Task 10.3–10.5 sections will need rewriting once this actually gets built, not just extended.

**Nothing has been migrated, no function has been altered, no test has been written.** This section is a design record for whoever picks this up next — could be this session resumed, could be someone else.
