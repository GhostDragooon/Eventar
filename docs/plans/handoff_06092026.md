### M4 — `/checkin/confirm` PassView state-ordering bug
`app/(public)/checkin/confirm/page.tsx:343-374`. Before this pass, the pre-checkin `PassView` branch order was `!selfServe → checkinState==='open' → checkinState==='early' → closed`. The `!selfServe` short-circuit fired FIRST and replaced everything — so a staff-only event's pass NEVER surfaced "Check-in opens at HH:MM" in the early state, even though the timing was fully knowable. An attendee opening their pass link the day before saw "Self check-in isn't enabled — please see reception." with no window information.

Reordered:
- `checkinState === 'early'` → always shows "Check-in opens at HH:MM on {date} — an hour before the event starts. Keep this pass handy."
- `checkinState === 'open'` → `selfServe` gets `ConfirmButton + "Tap when you arrive"`; `!selfServe` gets a NEW line "Check-in is open — please see reception with this pass." (replaces the old "isn't enabled" copy in the moment where it actually matters, without the misleading absence framing).
- `checkinState === 'closed'` → unchanged.

Verified live in all three states.

**No new test.** The reorder is a pure `PassView` change; `PassView` is not exported and the existing `page.test.tsx` scopes only PII regression. Exposing `PassView` to add a state test is scaffolding for scaffolding's sake. The re-walk covers it; if a future regression demands it, that's when to lift the surface.
