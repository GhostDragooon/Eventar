### 7.2 Found by execution, not in the plan (root causes)

1. **Open redirect at six `next` sinks (pre-existing at HEAD on the attendee pages; zero-click for any signed-in visitor).** `startsWith('/') && !startsWith('//')` lets `/\evil.example.com`, `/<TAB>/evil` and `/\/` through (browsers read `\` as `/` and strip tab/CR/LF). Fix: `safeNextPath()` resolves the string against a dummy origin, requires the same origin, and returns the ORIGINAL string; used at all six sinks (`/login` page + action, attendee sign-in page + action, sign-up page, `/auth/callback`); hostile cases are tested at every sink. [X]
2. **Next 16.2.12's bundled SWC drops the leading space of a multi-line JSX text node that follows an element, when the node also contains an HTML entity** (`&apos;`). TypeScript and vitest keep it, so every jsdom test passed while the browser rendered "ux-prac-1@example.comhas records". Two sites found by a repo-wide TS-vs-SWC comparison (`app/invite/[token]/page.tsx`, pre-existing `app/account/AccountClient.tsx`); fixed with explicit `{' '}`; **`tests/jsxWhitespace.test.ts` now compiles every component with both compilers and fails on the class.** [X]
3. **First Accept after a fresh sign-in always failed (user-lens F1, 4 of 4 fresh sessions).** Cause: PostgREST 14.15 answers `401 PGRST303 "JWT issued at future"` to part of a *burst* of requests (the invite check's three parallel reads) when that burst is the first PostgREST traffic after an idle spell and the token was minted after the clock reading PostgREST holds. Evidence: response header on the 401 (`www-authenticate: … JWT issued at future`, `proxy-status: PostgREST; error=PGRST303`); reproduced **with no app code** (standalone script: fresh token, ≥20 s PostgREST idle, 3 parallel reads → 1–2 of 3 refused; 0 of 54 refused with steady traffic, a single request, or ≤8 s idle) [X]. **Cause confirmed upstream:** PostgREST issue #5196 "PGRST303: JWT issued at future" (closed 2026-09-02), fixed in **14.18 and 16.3** (CHANGELOG: "Fix sporadic PGRST303 JWT issued at future errors"); the earlier attempt, PR #5159 "JWT validation uses wrong current time due to a bug in auto-update" (14.17 / 16.1), was not enough. The reviewer's reading of 14.15's source: `AppState.hs` serves the JWT's "now" from `mkAutoUpdate … getCurrentTime`, a cached clock that can be stale after an idle spell, while `Jwt.hs` allows only 30 s of `iat` skew; 14.18 uses `getCurrentTime` directly. [SOURCE: issue, PR and CHANGELOG fetched this session; the source files read by the reviewer, not by me.] **The local stack is pinned to 14.15 by the Supabase CLI**: upgrading the CLI to a release that bundles 14.18 or later removes the cause, and `retryStaleJwt.ts` carries a delete-when note. Fix: one retry, only for that exact header text, in the shared server client's `fetch` (`lib/supabase/retryStaleJwt.ts`, wired in `lib/supabase/server.ts`); a refusal happens before any SQL, so repeating is safe for every method. Live proof (Server Action path): 223 s of PostgREST silence, fresh sign-in, one Accept click → success, log shows two retries [X]. **The first version of this wrapper had two defects that only show inside a Server Component render, both found and fixed by execution (a stub "PostgREST" plus a temporary page, since removed):** (a) it awaited `res.body.cancel()`; Next hands every caller a `tee()`'d clone of one memoised response (`node_modules/next/dist/server/lib/dedupe-fetch.js`), and a tee branch's `cancel()` only settles when the other branch is cancelled too, so the render **hung for 60 s** with one request having reached the stub; (b) Next memoises an identical GET or HEAD per render, so a plain second call returns the same refusal (executed: every repeat variant, immediate, after `setTimeout(0)`, after a cancel, returned the memoised 401 with one real call per URL). The final wrapper does not await the cancel and retries with an `AbortSignal` (Next's documented opt-out): GET 200 and HEAD 200, two real calls each, render in 55 ms; the same logic without the signal ended on 401 [X]. Both behaviours have unit tests that fail under mutation. **Live proof, Server Component path:** after >10 min of PostgREST silence a practitioner signed in and landed on `/account/record`; that one render logged **seven** stale-clock refusals and still rendered completely (attendance, CPD section), no hang, no error [X]. That count is the real severity: without the retry, the first page a person sees after signing in during a quiet period is the one most likely to fail. **Not covered by the retry:** `proxy.ts` builds its own client (one request per navigation; no failure observed; add `global: { fetch: retryStaleJwt() }` there if it ever shows up), and the browser client. **Production exposure is unknown:** the hosted gateway masks the PostgREST version (`server: cloudflare`); check Supabase dashboard → Infrastructure for the Seoul project, and expect the Singapore project to run 14.x.
4. **Primary buttons rendered dark text on the blue fill (3.82:1 light, 1.96:1 dark; user-lens F5).** `cn()` is `twMerge(clsx())`, and tailwind-merge 3.6 does not know the project's custom type scale, so it reads `text-label-md` (a font size) as a text colour and evicts the Button's own `text-on-primary` (executed: merged string lacks it). Local fix at the two Band 1 sites that hit it (`components/auth/MagicLinkSignInForm.tsx` submit, the practitioner panel's primary control): `text-on-primary!` (Tailwind v4 important suffix, survives the merge) → **4.55:1 light, 7.59:1 dark** [X]. **Root cause is global and deliberately not fixed here (scope, rule 3):** five more default-variant Buttons lose their colour the same way (`app/events/[id]/edit/page.tsx:266`, `components/event-form/CreateEventWizard.tsx:170` and `:234`, plus the outline/destructive ones in `ManageWorkstation.tsx`), and three `cn()` calls lose their type size instead (`ActionGroup.tsx:24`, `PlanSelectionCards.tsx:33`, `PricingComparison.tsx:36`). Registering the ten custom font sizes with `extendTailwindMerge` in `lib/utils.ts` fixes all of them but visibly changes those three. Belongs to package G1 (token roles + usage sweep); decision for Ivan.
5. **The invite card sat under the sticky header** because it used `py-2xl`, and the spacing token is `xxl` (`--spacing-xxl`), so the class generated nothing. Now `py-xl` like the door pages: card top 52 px → 84 px against a 62 px header. [X]
