## What's MISSING per phase (concrete)

### Phase 2 — Registration flow (next up)

**New tables:**
- `registrations` — event_id FK, email, full_name, registered_at, registration_code (e.g. `WK-9X7P`), status (registered/attended/cancelled)
- `email_log` — purpose enum (confirmation/reminder/survey), event_id, registration_id, recipient_email, sent_at, status (queued/sent/failed)

**New routes:**
- `/events/[id]/register` (public, GET form + POST handler) OR a registration form inline on the public event page

**New Server Action:**
- `registerForEvent(eventId, formData)` — Zod-validates, writes `email_log` FIRST (per CLAUDE.md hard rule), inserts `registrations`, returns success or duplicate-email error

**New page:**
- Registration success page (or in-place success state)

**RLS policies:**
- anon INSERT on `registrations` (gated by event_id pointing to a published event)
- organizer SELECT on their event's registrations
- no SELECT for anon (privacy)

**Critical hard rule from CLAUDE.md:**
> Insert email_log row FIRST, send email SECOND. Reverse order risks duplicate sends on retry.

For Phase 2 the "send" is just `console.log('[email stub] would send confirmation to X')`; the email_log row still goes in first so when we wire Resend in Phase 7 the order is already right.

**Demo at end of Phase 2:** anon visitor lands on `/events/[id]` → clicks Register → fills name + email → success → server log shows "would have sent confirmation". Try same email twice → friendly duplicate error.

### Phase 3 — Publish + static QRs

- `qrcode` npm dep
- Two QR PNGs generated server-side on publish:
  - `/events/[id]` (info QR — for the audience)
  - `/events/[id]/register` (registration QR — for the audience)
- Download buttons on the edit page
- Maybe: full edit UI (per the Phase-1 note, "full edit form deferred to phase 3")

### Phase 4 — Check-in (tablet)

- `registration_code` is generated on registration insert (e.g., trigger or RPC)
- New route `/events/[id]/checkin` (staff-gated; already in proxy matcher)
- Tablet UI: input for code or scan a personal QR URL
- Supabase Realtime channel on `registrations` table so multiple tablets see live updates
- `attended_at` column on `registrations`
- Personal QR per registration (URL: `/checkin?code=WK-9X7P`) — generated on registration confirmation

### Phase 5 — Survey

- `survey_responses` table — registration_id FK, ratings (jsonb or columns), comment, submitted_at
- `/survey/[event_id]?code=WK-9X7P` route — validates code, shows 3-5 question form, submits
- Email stub: "would have sent survey to X"

### Phase 6 — Analytics

- Per-event page: registered count, attended count, attendance %, avg ratings, comments list
- Manager dashboard: every event with totals
- Pure read-side; no new tables
