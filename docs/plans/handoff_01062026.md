## Architecture decisions worth remembering

1. **5-state lifecycle DERIVED, not stored.** `computeLifecycle(event, nowMs)` returns one of 6 strings from existing `status` + `start_time` + `end_time` + new `registration_close_at`. Avoids enum migration. The "48h auto-complete" rule from the design doc is subsumed by `nowMs > end_time` in the helper (simpler — both paths reach the same `completed` lifecycle). When Phase 9 (pg_cron) lands, a scheduled `UPDATE events SET status='completed' WHERE status='published' AND end_time + interval '48h' < now()` would flip the row; helper continues to work because it short-circuits on `status='completed'` first.

2. **Reopened Q16 Decision A (Phase 6's "two-layer split with surfaces").** Phase-6 `LayerOneTiles` (Capacity Utilization · On-time Arrival) removed from `/dashboard`; replaced by the General Category band. Capacity's cross-event aggregate dissolves into per-event Capacity Gauge on `/details`. On-time Arrival relocates to `/details` Section B (Completed-only) where the per-event lens is coherent — per user feedback during brainstorming ("time arrival does not matter on the day does it?"). The design doc records this reopen explicitly in §Decisions A.

3. **Visual language: M3 tokenized restraint codified.** `frontend-design:frontend-design` skill invoked in its INVERSE mode (consistency-over-novelty) because Phase 4.6 already locked the M3 indigo system. The design doc has a full Visual Language section documenting token usage maps, the 6 StatusPill specs, and the custom `livePillBgPulse` keyframe rationale (animates `background-color` only, not opacity — preserves text legibility, rejects `animate-pulse`). Mockup at `docs/plans/phase-6.5-mockup.html` shows the locked picks + the rejected variants for reference.

4. **`updateRegistrationClose` action lives in `app/events/[id]/details/actions.ts`**, not `app/events/[id]/edit/actions.ts`. Plan deviation: original Task 5 said "extend the edit form," but `/edit/page.tsx` is read-only ("Editing event details isn't available yet — this view is read-only. Need a change? Ask an admin."). Inline editor lives in `/details` Section A where the operational settings naturally belong. The /edit Operations ActionCard points users at /details via "View details" CTA.

5. **Single-clock-per-request discipline.** Every Server Component computes `nowMs = Date.now()` exactly once at the top and threads it through props to all consumers (sections, helpers). Prevents lifecycle-derivation drift between independently-rendered sections at boundary timestamps. Dev-lens caught a violation in `FeedbackSection.tsx::timeAgo` (called `Date.now()` directly); fixed by passing `nowMs` as a prop.

6. **`groupByLifecycle` overloaded for two call patterns.** Original: `groupByLifecycle(events, nowMs)` derives lifecycle per row. Added: `groupByLifecycle(items, getLifecycle)` accepts a key extractor for callers (like the dashboard) that have already decorated items with lifecycle. Cleanest way to honor "wire the helper or delete it" (dev-lens finding) without forcing a duplicate `computeLifecycle` call.

7. **Cancelled rendered separately from the main lifecycle order.** Not part of the chronological flow (drafted → registering → upcoming → live → completed). Renders as a separate `EventLifecycleSection` collapsed by default, only when cancelled events exist. Status pill uses `bg-error-container/30` (same family as Live's red, but muted and static).

**Seed**: 6 events covering all 5 lifecycle states (drafted, registering, registering-with-future-close, upcoming, live, completed) + 5 registrations on the Completed event (4 attended, 1 no-show, all check-ins within 15 min of start) + 3 survey responses (1 with comment "Loved the panel and the networking break.", 2 silent).

**Verifications**:
- **Lifecycle derivation**: SQL `CASE` mirror of `computeLifecycle` returned the expected lifecycle for each of 6 events. After fixing my initial seed (where Upcoming's `close_at` was off by a few hours and rendered as Registering), all 5 lifecycle states reachable.
- **Section B math** (queried via the same shape `/details` runs): `registered=5 · attended=4 · on_time_pct=100% · last_signup=2026-04-05`. Matches design intent.
- **Section C math**: `total_count=3 · latest comment present`. With `count: 'exact'` added in the F#7 fix, the page now reads "3 of 4 (75%)" + "Latest comment · 2 more in analytics" + the quoted comment.
- **Dashboard By Status math**: `drafted=1 · registering=2 · upcoming=1 · live=1 · completed=1` — Tile renders these as a segmented bar with corresponding legend.
- **Dashboard Days Until Next**: min start_time was the Live event itself (start was 30 min ago). With Fix #4 (`nextIsLive=true`), tile renders headline "Live" + event title — instead of the confusing "0" the reviewer flagged.
- **`updateRegistrationClose` round-trip**: set close_at to past → derived lifecycle flipped Registering → Upcoming; cleared back to null → flipped back to Registering. Validates the Server Action + lifecycle helper work end-to-end against the real DB.
- **Cleanup**: cascade delete via FK removed all rows. 0/0/0 BACKTEST events/registrations/surveys after cleanup. No residue.
