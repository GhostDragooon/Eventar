## Verified OK

- Function hygiene [X]: SECURITY DEFINER, `search_path = public, pg_temp`, owner `postgres`, `proacl` = postgres, authenticated, service_role only (no PUBLIC, no anon). Every call inside is schema-qualified or in pg_catalog.
- `resolve_actor` [X]: the override is honoured only when `auth.role() = 'service_role'`; hand test as a signed-in org-A admin with an org-B admin's staff id: refused 42501. For a real session `p_actor_override` is inert.
- Org check then lock, in that order, is the right order (a foreign caller never takes the row lock). The gap between the org read and the lock needs `event_id` or `events.organisation_id` to change, and no signed-in path can change either [R].
- Behaviour [X, all rolled back]: clash gives `already_registered` 23505; no-op writes no audit row; name-only edit writes `{"fields": ["full_name"]}`; both-field edit writes `["full_name","email"]`; audit row carries `actor_user_id`, `actor_role`, and the registration's organisation; payload and messages hold no name or email.
- Bypass closure [X]: `relacl` shows anon `r`, authenticated `rd` (SELECT, DELETE), service_role and postgres keep UPDATE; `attacl` empty (no column grants); no UPDATE policy remains; no view or rule depends on registrations; no PUBLIC entry. Direct UPDATE as authenticated and as anon: `permission denied for table registrations`. Direct DELETE as authenticated: 0 rows.
- Writers of registrations [X]: five SECURITY DEFINER functions, all owned by postgres (`mark_attended`, `self_check_in`, `claim_registrations_for_user`, `sync_registration_checkin_summary`, the new one); the only SECURITY INVOKER functions that mention the table are `get_org_participants` (read), and the two guard triggers. `mark_attended` run end to end as a signed-in organiser: status `attended`, method and time stamped. service_role UPDATE still works. Event delete cascades registrations. Users ON DELETE SET NULL runs as the table owner, which keeps UPDATE [R: RI actions run as the owner of the table they modify].
- Callers [X]: no `.update(` on registrations anywhere in app/, lib/, components/, scripts/ outside tests; the only two other tests that update registrations (`self_check_in.rls.test.ts:570`, `tests/cpd/attendance_issuance.rls.test.ts:368`) use the service-role client.
- Migration [X]: re-applies cleanly inside a rolled-back transaction (idempotent, DO check passes). Timestamp is later than every existing migration. `seed.sql` grants at line 22 and revokes at line 198, so the order is right. Replay gate 6 query returns false for authenticated.
- Gates [X]: `vitest run` on the action test 12/12; eslint on the seven touched TS files, 0 findings; `tsc --noEmit` clean.
- Test arithmetic [R]: 473 to 494 equals 19 new + 1 audited row + 1 net in link-immutability.
- `updateAsRoleWithGrant` [R]: grant and the allow-all policy are created inside one transaction that is always rolled back in `finally`, so nothing is visible to other sessions at any point and nothing is left behind on a failure path; `CREATE POLICY` takes ShareUpdateExclusive, which does not block DML, so parallel files are not disturbed.
- Participation evidence [X]: the table does not snapshot registrant name or email, so editing them cannot diverge a chain.
- A `participation_evidence_actor_id_fkey` WARNING from `mark_attended` in my scratch run came from my fixture (random JWT subject with no `public.users` row); not DB-05.
