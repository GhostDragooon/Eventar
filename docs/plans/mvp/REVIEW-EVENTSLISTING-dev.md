## Verified OK

- Same definition of upcoming and live [R]. `computeLifecycle` for a published event returns `completed` only when `nowMs > endMs`, and every other published state (`live`, `upcoming`, `registering`) is what the old JavaScript filter kept. `end_time >= now` is therefore exactly the complement, boundary included: an event ending at exactly now stays listed in both versions. Test 3 and mutant A5 (`now + 1 ms`) pin that boundary [X].
- Instants, not calendar dates [R]. The comparison is `new Date(nowMs).toISOString()` against `timestamptz`. No `getDate`, `setHours`, or zone arithmetic was added, which is what the `eventar-timezone-correctness` skill asks for. The `Intl.DateTimeFormat` calls for the card day, month and time already pass the event's own `timeZone`.
- One clock [R]. `nowMs` is read once, before the query, and feeds both the DB filter and `computeLifecycle`. The page is `force-dynamic`, so it is per request. The millisecond-precision value in the URL cannot be served stale by any fetch cache.
- Over the cap, the soonest events survive [X]. Test 2 (105 upcoming, fed in reverse) returns 100 with first `Upcoming 0` and last `Upcoming 99`; removing `.limit` fails it (A6). Reversing the sort fails three tests per the author's mutant M5 and the fake's behaviour. Only the furthest-future events fall off, with no notice (disclosed as a design question in the hand-back; not a defect of this commit).
- Soft-deleted rows stay excluded [X][R]. The query keeps `.is('deleted_at', null)`; the anon and authenticated policy `events_public_read_published` is `(status = 'published') AND (deleted_at IS NULL)`. Mutant A3 (remove the `.is`) fails test 4.
- Test fails without the fix [X]. Mutant A1 (remove the `.gte`) fails tests 1 and 3. The clock is pinned with `vi.useFakeTimers({ toFake: ['Date'], now })` and restored in `afterEach`, so the file does not depend on the hour it runs (matches the `time-dependent-test-fixed-clock` rule). Mutants killed: A1, A3, A4 (`start_time`), A5, A6.
- No other consumer of this query [X]. `EventsListClient.tsx` has no past view (grep for past, completed, ended: no match). Only `page.tsx` builds the public listing; the other 20 files that read `events` are per-id or staff-scoped. `end_time` is NOT NULL, so no row is dropped by NULL comparison.
- Gates on the touched files [X]: `pnpm exec vitest run` on `page.test.ts`, `exportBatching.test.ts` and `app/dashboard` gave 4 files, 33 tests, all passed. `pnpm exec eslint` on all touched files in both commits: exit 0, no output. `pnpm exec tsc --noEmit`: exit 0.
