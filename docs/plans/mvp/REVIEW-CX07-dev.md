## Verified OK

[X] Real `@supabase/postgrest-js` 2.105.4 against a stub `fetch`: a 2-row array through `.select('id').eq().eq().maybeSingle()` returns `data: null`, `status: 406` and `error: { code: 'PGRST116', details: 'Results contain 2 rows, ...', message: 'JSON object requested, multiple (or no) rows returned' }`. The error is a plain object, not an `Error`. One row returns the row, zero rows returns `data: null` with no error, a server error keeps its own code (57014). [R] `node_modules/.pnpm/@supabase+postgrest-js@2.105.4/.../dist/index.cjs:359-370`: for `maybeSingle()` on a GET the code is synthesised client-side, so PostgREST itself is never asked for a single object. [X] Local stack, read-only: the local database already holds one email with two active `staff` rows (I did not create it; 71 active rows, 1 duplicated email; likely a fixture from the live-backtest agent). With a locally minted JWT carrying only that email claim (no auth writes, no inserts), `GET /rest/v1/staff?select=id&email=eq.<it>&status=eq.active` with `Accept: application/json` returned 200 and 2 rows under the real `staff_self_read` policy (`email = auth_email()` ...). With `Accept: application/vnd.pgrst.object+json` the server itself answers 406 `PGRST116` "Cannot coerce the result to a single JSON object". So PGRST116 is the only code the two-row case can produce, from either side.
