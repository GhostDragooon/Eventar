## What it does
- `update_event_with_blocks` is a per-block upsert keyed by block id. A payload block with an `id` updates that block (the id must belong to the event and appear once); without an `id` it is inserted; a block left out of the payload is removed, unless a survey answer points at it (`survey_responses.valuable_block_id` is ON DELETE SET NULL, so the old delete-and-reinsert silently orphaned the answer): then the whole save is refused with SQLSTATE 22023 `block_has_survey_answers: <title>` and nothing is saved. `display_order` is the payload index. A missing or null `topics` is an empty list, as on create. One transaction.
- A published event is not edited, at every layer a signed-in user can reach (Ivan's ruling, UPD-01): the RPC locks the event row (`for no key update`, the lock `publish_event`'s UPDATE takes, so a publish waits for a save to commit and FK checks do not), treats a soft-deleted event as not found, refuses any status but draft with `event_not_draft` (22023) for every role, and its UPDATE carries `and status = 'draft'` plus a row-count check; a BEFORE UPDATE trigger on `events` refuses a change to any column but `registration_close_at` when the row is not a draft; a BEFORE INSERT/UPDATE/DELETE trigger on `agenda_blocks` refuses any write unless the parent is a draft (a block cannot be moved onto or off a published event) and a direct DELETE of a block a survey answer points at.
- The triggers hold `authenticated` and `anon` only (`current_user`): the definer functions (publish, cancel, complete, bulk status), FK cascades and `service_role` (server code, scripts, test teardown) pass; the RPC itself refuses a non-draft for `service_role` too.
- `update_event_with_blocks` is no longer executable by `anon` (it was, through PUBLIC; it died at the table grants, now it dies at the door).
- Cross-organisation callers get a clean 42501 "event ... is not in your organisation" on an event they can see; on another organisation's draft they get "not found or not visible" (no existence leak).
- `updateEvent` returns `blockIds` (read back in `display_order`, which is the payload index; a count mismatch is an error, not a wrong mapping). The form keeps a map localId to database id, seeded from the loaded blocks and overwritten by each save's `blockIds`, and sends it as `id`, so a second save updates instead of duplicating. The refusals are plain sentences, including "The agenda changed in another tab or window, so your changes were not saved. Reload this page and try again." for a block id a second tab already removed.

## Deviations from the card text, and why
1. `registration_close_at` is NOT protected by the events trigger. The Close registration editor on the details page (`app/events/[id]/details/actions.ts:63`) writes it on a published event through the user-scoped client; protecting it would break a shipped feature (the backtest confirmed it still works).
2. The card says the RPC org check "needs an operator exception". It is NOT added: the platform operator's UPDATE would match zero rows without UPDATE policies on `events` and `agenda_blocks` (the operator has only SELECT there), and adding write policies is a privilege change. The RPC refuses an operator from another organisation with a clean 42501; `updateAction.ts` and its test now say the RPC decides. Ivan's call below.
3. The survey-answer check is a definer helper (`app_private.block_has_survey_answers`), so it does not depend on what the caller's RLS lets them read. It is in `app_private`, which PostgREST does not expose, so the dev lens's "existence oracle" is not reachable over the API.
4. The trigger compares every column but `registration_close_at` (`to_jsonb(new) - ... is distinct from to_jsonb(old) - ...`) instead of the 22 granted columns by name (dev lens F12): shorter, and a column granted later is covered without editing the trigger. The grant-drift test stays.

## Needs Ivan
1. **The self-serve check-in kill switch cannot be flipped on a live event.** `checkin_modes` is protected, and the edit form (the only place it is set) is closed to published events since UPD-01, so an organiser cannot turn self-serve QR check-in off while the event runs (`event_checkin_modes.rls.test.ts` still calls it "the kill switch" and proves it on a draft). Options: (a) as built, the cost of "nobody edits a published event"; (b) exempt `checkin_modes` like `registration_close_at` and add a small control on the details page (a front-end card).
2. **Platform operator editing another organisation's draft** is refused cleanly. To allow it: an UPDATE policy on `events` and an ALL policy on `agenda_blocks` for `app_private.is_eventar_staff()`; the draft-only triggers would still hold.
3. **After the survey-answer refusal the form still shows the removed block** while the database keeps it, and Save repeats the refusal until the page is reloaded (user U1, executor question 1). Before: the sentence says "Nothing was saved." beside a block that looks removed. Options: (A) add "Reload this page to bring it back." to the sentence (cost: loses other unsaved edits); (B) put the block back in the form on this refusal (cost: form state code); (C) disable Remove on blocks with survey answers (cost: needs the answered ids passed to the form). A draft normally has no survey answers, so this is rare.
4. **A published event's `/edit` page is a read-only summary** under the heading "Edit" whose only explanation is at the bottom: "Editing event details isn't available yet — this view is read-only. Need a change? Ask an admin." (user U2). An admin reads it as a dead end, and "yet" promises what the UPD-01 ruling does not. Options: move the sentence to the top; say "Published events cannot be edited. Registration close can still be changed on the details page."; drop "Ask an admin" for admins. Copy pick, not applied.
5. A block with survey answers can never be deleted from the UI (same cause as 3).
