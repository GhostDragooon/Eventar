## Q2. Migration semantics

- `REVOKE ... ON ALL TABLES IN SCHEMA` covers views and foreign tables: PG 17 GRANT docs, "ALL TABLES also affects views and foreign tables, just like the specific-object GRANT command" [R]. The docs are silent on materialized views and partitioned tables; from memory of `aclchk.c` the OBJECT_TABLE case also lists RELKIND_MATVIEW and RELKIND_PARTITIONED_TABLE [I, not executed]. Local has 0 views, 0 matviews, 0 foreign tables [X], so those arms are untested here. The self-check lists relkinds `r,p,f,v,m`, so a miss fails closed.
- Table-level REVOKE removes column grants: REVOKE docs, "When revoking privileges on a table, the corresponding column privileges (if any) are automatically revoked on each column of the table, as well" [R]. Locally no `pg_attribute.attacl` entry mentions anon [X]. The migration header claim is right.
- Grantor semantics: see F7. Docs quotes are in that row. Local grantor for every entry is `postgres` [X].
- Default privileges: per-schema form is correct. It reverses the per-schema GRANT that `init_staff.sql` restates. The ALTER DEFAULT PRIVILEGES docs warn that "you cannot revoke privileges per-schema if they are granted globally", which is why the schema-less form (1c) is there. Both are idempotent (revoking an absent privilege is a no-op). Local `pg_default_acl` for postgres, schema public, tables [X], decoded: `anon = MAINTAIN, REFERENCES, SELECT`; `authenticated = DELETE, INSERT, MAINTAIN, REFERENCES, SELECT, UPDATE`; `service_role = same as authenticated`; `postgres = all`. Raw: `postgres|public|r|{postgres=arwdDxtm/postgres,anon=rxm/postgres,authenticated=arwdxm/postgres,service_role=arwdxm/postgres}`. There is no schema-less row for `postgres` after the migration, so 1c created none (as the header says). REFERENCES and MAINTAIN stay on anon; the TRUNCATE migration header already records why (needs SQL as the role).
- Self-check [R]: sound. `has_table_privilege('anon', oid, 'DELETE')` and `has_any_column_privilege(..., 'INSERT'|'UPDATE')` include PUBLIC and inherited grants. I replayed the sweep predicate as a read-only count: 0 rows [X]. PUBLIC holds no table privileges at all locally [X], so `from public` is a no-op here and cannot strip another role's access.
- Migration recorded as applied locally: `schema_migrations` row `20261023140000` [X]. It is the newest migration, nothing later re-grants.
