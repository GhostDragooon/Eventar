Behaviour:
1. Both Publish controls ask first with a dialog that names the event and says what goes public, what starts (registration opens now or on its date; check-in opens 60 minutes before the start, in the event's own timezone) and that details cannot be edited yet. The create form validates first, so an invalid form never opens it; Save draft never opens it.
2. Publishing lands on `/events/<id>/details?published=1`: a Published banner (focused, so it is announced) and "What to do next": share link with Copy link (confirmation driven by the result), where registrations show, when check-in opens.
3. Save draft lands on `/events/<id>/edit?saved=1`: "Draft saved. Review and publish when you are ready." (a role that cannot publish reads "Draft saved. Publishing needs an organiser admin."). The banner turns into "You have changes that are not saved." the moment the form changes and back to saved after Save changes. The flag is removed from the address on arrival.
4. The Publish card sits outside the form and publishes the last saved version, so it refuses while the form has unsaved changes (the form reports its state through `lib/draftDirty`).
5. A 22023 refusal ("no longer a current draft") shows inside the dialog with Manage as a link and only Close; closing it refreshes the page so the DRAFT badge and Publish card go.
6. The one-way warning is tied to the Publish button with `aria-describedby`. The stale docstring at `edit/page.tsx` (about line 459) now says what the card does.
