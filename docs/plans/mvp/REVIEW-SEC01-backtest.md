## Verified OK

1. **Direct anon writes, all refused at the grant layer [X].** `ANON_KEY` only, no JWT, POST / PATCH / DELETE on accrediting_bodies, agenda_blocks, consent_records, events, organisations, organisers, registrations, speaker_checkins, staff, survey_responses, users, invite_tokens, audit_events: 39 of 39 returned HTTP 401 with SQLSTATE 42501 and message `permission denied for table <name>`. None returned an RLS message ("new row violates row-level security policy"), none succeeded.
2. **Grant sweep [X].** 35 relations in `public` (all tables, no views): `anon` holds none of INSERT / UPDATE / DELETE, and no column-level INSERT / UPDATE (`information_schema.column_privileges`). 28 relations keep anon SELECT, 7 have none. A table and a view created as postgres inside a rolled-back transaction: anon = SELECT only (no I/U/D/TRUNCATE/TRIGGER); authenticated and service_role = DISU+S on the table. The probe left no object behind (`count=0`).
3. **Anon reads unchanged [X].** `/rest/v1/events?status=eq.published`: 81 rows, equal to the psql count of 81 published events. `accrediting_bodies`: 67 visible (RLS), `agenda_blocks`: 1 of 1. Every PII table (`registrations`, `staff`, `users`, `survey_responses`, `invite_tokens`, `audit_events`, `consent_records`, `organisers`, `organisations`, `speaker_checkins`) returned 0 rows through RLS. The public event page `/events/<id>` rendered the fixture, HTTP 200. SELECT grants are untouched by construction [R].
4. **invite_tokens, service_role [X].** `POST` 403 / 42501, `PATCH` 403 / 42501 (hint "GRANT … TO service_role"), `DELETE` 204 on a bogus id, and a real DELETE (`created_by=eq.<admin>`, `Prefer: return=representation`) returned both rows I made (one accepted, one open) and the table went back to its pre-run 15 rows. ACL is `service_role=rdxm` (SELECT, DELETE, REFERENCES, MAINTAIN), `authenticated=rxm`, `anon=rxm`. `authenticated` (an org admin JWT) POST / PATCH / DELETE: 403 / 42501 "permission denied", so the audited table is definer-only for every API role.
5. **service_role elsewhere [X].** registrations, survey_responses, users, events, organisations, consent_records, accrediting_bodies, agenda_blocks, organisers, speaker_checkins: DISU. `staff`: DIS plus column-level UPDATE (`has_any_column_privilege` true, table UPDATE false), as `seed.sql` HEAD asserts. `audit_events`, `credit_ledger`: SELECT only. Real use: Server Action inserts into `registrations`, `email_log`, `survey_responses` (flows below) and deletes in cleanup all worked as service_role.
6. **Role changes beyond the two intended [R]/[I], not [X].** I had no pre-migration snapshot, so this is not a before/after diff. The migration text only touches `PUBLIC` and `anon` (table-level and default ACLs) and `service_role` on `invite_tokens`. Every non-full row in the live matrix for `authenticated` and `service_role` maps to a revoke already present in `git show HEAD:supabase/seed.sql` or an earlier migration (events: `revoke insert, update … from anon, authenticated`; staff; email_log and rate_limits `revoke all`; occurrences / checkins / evidence; audit and ledger tables). Rows I could not map to HEAD seed text (`credit_disputes` auth `IS`, `professional_profiles` auth `ISU`, `data_subject_requests` auth `S`) are consistent with their own migrations and are not touched by SEC-01. Treat this item as "no unexplained change seen", and rely on the coordinator's `test:rls` (seed posture test) for the rest.
7. **Registration, guest [X].** `registerForEvent` via `Next-Action` POST to `/events/<id>`: HTTP 200; row read back from psql: `status=registered`, `user_id` null (guest), `registration_code` set, linked `email_log` row `queued` (stub: `RESEND_API_KEY` unset).
