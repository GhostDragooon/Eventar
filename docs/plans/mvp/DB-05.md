## The hole [X]
`registrations_org_member_update` plus the table UPDATE grant let any organisation member rewrite any column of any registration of their organisation through PostgREST: `status = 'attended'`, `check_in_at`, name, email, `registration_code`, with no audit row and outside the check-in window DB-02 enforces. A trigger guarded only `user_id`, `profile_snapshot` and `source`. The new tests' PATCH cases succeeded before the migration. Nothing in the app updates registrations as a signed-in user (grep of app/lib/components/scripts, the four SQL functions that do are definers: `mark_attended`, `self_check_in`, `claim_registrations_for_user`, `sync_registration_checkin_summary`).

## What it does
- `public.update_registration_contact(p_registration_id, p_full_name, p_email, p_actor_override default null)`, SECURITY DEFINER: the actor is resolved (organiser_admin, organiser_member or eventar_staff; body_admin and auditor are refused, anon cannot execute), the registration must be in the actor's organisation (`eventar_staff`: any), its event not soft-deleted; the row is locked `for update` and re-read, so a registration linked to an account while the edit waits is seen as linked. Name 1 to 200 characters, email a plausible address of at most 254 (stored lower-case). Saving the same values is a no-op with no audit row. A linked registration (`user_id` set) keeps its email (`linked_registration`, 22023); its name can be corrected. An email another registration of the event uses is `already_registered` (23505). The code, status and check-in are never touched. The audit row `registration_contact_updated` is written last, with the NAMES of the fields changed and nothing else.
- `revoke update, delete on public.registrations from anon, authenticated` and `drop policy registrations_org_member_update`. DELETE goes too (backtest F2): no policy admitted it, a signed-in DELETE answered 200 with no rows, and a grant with no policy is one policy away from erasing registrations; nothing in the app deletes them as a user. `service_role` keeps both (cancel, claim, erasure, scripts, teardown). Re-asserted in `seed.sql`, checked by the CI replay gate and the audited-writes matrix. The dead anon INSERT policy stays (SEC-01 keeps it as defence in depth and its tests use it).
- The function RETURNS the registration's event id (dev F8), so the caller refreshes the right pages: the Server Action is `updateRegistrationContact({ registrationId, fullName, email })` (no `eventId` argument; a mismatched pair could otherwise edit one event's row and refresh another's pages) in `app/events/[id]/registrations/actions.ts` for UX-04's dialog: `requireStaff()` first, Zod, the RPC through the user-scoped client with `p_actor_override: staff.id` (inert for a real session, proved), the refusals in plain sentences, an unmapped failure logs the registration id and the code only, revalidates checkin, details and registrations of the returned event. Hand-off change for UX-04: no event id to pass.
