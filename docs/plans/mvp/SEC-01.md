- 20261023140000: `anon` loses INSERT, UPDATE and DELETE on every table and view in `public` (11 tables held it: accrediting_bodies, agenda_blocks, consent_records, events (DELETE), organisations, organisers, registrations, speaker_checkins, staff (INSERT, DELETE), survey_responses, users) and the default privileges for `postgres` stop granting it (per-schema and schema-less rows). `invite_tokens`: `service_role` INSERT and UPDATE revoked, DELETE kept; `create_invite_token` and `accept_invite_token` are SECURITY DEFINER owned by postgres and unaffected. - 20261023150000 (found by the backtest, F1): `authenticated` loses INSERT on `registrations`. The INSERT policy was `TO {anon, authenticated}` and checked only that the event is published, so a signed-in visitor (anyone can get a JWT through the attendee magic link) could POST `/rest/v1/registrations` directly and land a row past capacity (an event capped at 2 held 3), outside the windows, past the rate limit, without an `email_log` row, under anyone's email [X]. Registration is a Server Action with the service-role client; nothing inserts registrations as a signed-in user [R, dev lens Q1]. The policy stays as defence in depth.
- `seed.sql` re-asserts both with one statement each; the CI replay gate (`scripts/ci/replay-and-verify.sh`) now fails if anon holds DML anywhere, `service_role` holds INSERT or UPDATE on `invite_tokens`, or `authenticated` holds INSERT on `registrations` (queries run here against the local DB: clean, and they name an injected offender [X]; the script itself was not run, it starts with `supabase db reset`).
