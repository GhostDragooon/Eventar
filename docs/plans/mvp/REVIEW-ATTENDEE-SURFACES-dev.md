## Walk of status x time (finding 2 of the brief)

| Registration | Event state | Registrations | Check-in | History |
|---|---|---|---|---|
| registered | before window | Upcoming ("Registered") | "Opening soon" only if the window opens within 24 h | - |
| registered | in window (start-60 to end) | "Check-in is open" + pass | "Open now" + pass | - |
| registered | ended, no check-in | - | - | yes (pill reads "registered", pre-existing copy) |
| attended | in window | "You are checked in", no pass | "Open now", "You are checked in", no pass | - (arrives when the event ends) |
| attended | ended | - | - | yes |
| cancelled | any time | - | - | yes, future ones included (log semantics) |
| any | event row missing | - | - | yes, "Event removed" |
| registered/attended | event cancelled / draft / soft-deleted, future | **Upcoming, wrongly** | **pass, wrongly** | - (finding 1) |

Every registration lands on exactly one page per bucket, and none falls through all three, apart from the 100-row cap (finding 2). Registrations and Check-in overlap on purpose: both are views of live/upcoming.

## Brief items found clean

- Data exposure (item 3): `registration_code` is selected through the cookie client with `.eq('user_id', auth.userId)` after `requireAuthenticatedSelf()`, so it is the caller's own rows only. I found no column-level grant/revoke on `registration_code`. The `/checkin/confirm?code=` link is the same URL the confirmation and reminder emails already carry. That page is per-IP rate limited, robots noindex, and does not select `full_name`. It adds no new enumeration vector. Referrer: same-origin navigation, and the browser's default `strict-origin-when-cross-origin` strips the query cross-origin. The code is a bearer token for the pass, not personal data, so the PII-in-query rule is not engaged beyond the existing flow. Link prefetch: the confirm route has no loading.js, so Next 16's default prefetch fetches only the shared layout segments (link.md:302). Prefetch does not run the page's admin lookup or rate-limit counter.
- Persona boundary (item 4): every emitted link is `/events`, `/events/{id}` (public), `/account/registrations`, `/checkin/confirm?code=` or the shell's `/account*`. app/account/layout.tsx redirects staff sessions before any page renders. `/account/registrations` and `/account/check-in` classify as `attendee` in `classifyPath`, so they survive `attendeeNextPath` on the sign-in round trip.
- Next 16 (item 5): both pages are `force-dynamic` and read cookies through `supabaseServer`, so nothing per-user prerenders. `server-only` in loadMyRegistrations.ts is correct, since only server components import it. `Date.now()` is called once per render and handed down as one snapshot. That justifies the `react-hooks/purity` disable.
- Shell (items 7, 8): the longest-prefix `currentLabel` is correct and tested (`/account/profile` resolves to Account, `/account/record` to History). StaffShell's own Soon chip is untouched, and no other component or test depended on AccountShell's Soon rows. The record page sort order ("past stays in the action's order, newest first") matches the action's `event_start desc, nulls last`.
