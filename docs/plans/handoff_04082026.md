## 3. The defect that no gate could have caught

Both landed migrations `create or replace`d **the same two event RPCs**, each written from the *live* definition as its baseline — correct practice in isolation, and the check-in migration even documents doing so. `create or replace function` is a whole-body overwrite with no merge and no conflict detection, so the later timestamp wins outright.

Git saw no conflict (separate files). `tsc`, `eslint`, `vitest` and `next build` cannot see inside a function body. **Every gate was green while the database was broken.**

Proven by replaying both in timestamp order inside a rolled-back transaction:

| Fact after replay | Value | Consequence |
|---|---|---|
| `update_event_with_blocks` still names `status` in its SET list | `true` | — |
| `authenticated` holds UPDATE on `events.status` | `false` | **every organiser edit 42501** |
| `create_event_with_blocks` calls `publish_event()` | `false` | **publish unaudited again** |
| RPCs write `checkin_modes` | `true` | later migration won wholesale |

The column-privilege check runs against the **SET list, not the value**, so naming an unwritable column breaks every edit even when the value is unchanged — `20260802182411`'s own header warned of exactly this and the other branch could not see it.

Fixed by `20260803120000_reconcile_event_rpcs` — a third migration carrying the union of both intents, rather than editing either file (`20260803023000` was already applied to the shared local stack; history is append-only).

**Rule for concurrent agents touching SQL functions: two branches that both `create or replace` the same function are in conflict even when git says they are not.**

## 5. DEFERRED item 56 — CLOSED

The Stage-8 blocker. `set_event_cpd_config` gated on the caller (role, ownership) and the body (exists, active) but nothing modelled whether the caller's **organisation** could legitimately claim that body.

**The red test demonstrated the hole rather than describing it:** as a real `organiser_admin` JWT against an unrelated body, the RPC returned `expected undefined to be '42501'` — no error — and `events.accrediting_body_id` was written. 8/8 green after.

`20260804000000_organisation_body_authorisations`: an explicit `organisation × body × status` allow-list, unique pair, checked inside the definer.

Three judgement calls worth keeping:
1. **The check reads the EVENT's organisation, not the actor's, with no `eventar_staff` exception.** Platform staff configuring a tenant's event still cannot claim a relationship that tenant lacks — the body's authority is not ours to override. (This differs deliberately from the ownership check directly above it, which *does* except `eventar_staff`.)
2. **Clearing stays ungated.** Withdrawing a claim is never an assertion of authority, and an organiser must be able to undo *after* a body revokes them.
3. **Backfilled from reality, not blanket-granted.** Every `(organisation, body)` pair already in use on an event became active, so nothing in flight was stranded — but nothing else was granted, so the gate bites from minute one instead of being a no-op for the default org.

Hard Rule 11 posture proven by negative test (`42501`, not merely RLS-denied). **Still deferred to Stage 10:** the body-driven approval workflow. Rows are service-role-seeded until then.
