## The CRITICAL finding and fix (dev-lens)

**The first cut's free-text fallback was dead code — the CSV emitted the literal string `other` for Specialty/Position/Profession**, silently wrong on the dominant path, not blank. Root cause: `profile?.specialty_code || profile?.specialty_other || ''` — `'other'` is a real, seeded, truthy code (not null/empty), so `||` always short-circuits on the code before ever reaching the free-text override the code is a sentinel for. My own dry-run fixture happened to use `specialty_code: null` (not the literal `'other'`), so it passed without exercising the actual bug. `build_profile_snapshot()`'s free-text gap (my stated reason for reading live in the first place) was real, but the fix I wrote for it didn't work.

**Fix**: `labelOrFreeText()` in `collegeExportProjection.ts` now checks `code === 'other'` explicitly and falls through to the free-text field on that sentinel, and joins `professions`/`positions`/`specialties` (all publicly-readable controlled-list tables with `code`→`label_en`, added 2026-09-16) so every other code resolves to its human label instead of the raw snake_case value — a second real gap (dev-lens M1) the same rewrite closes. **Regression test**: `collegeExportProjection.test.ts` — `"specialty_code/position_code = 'other'... falls through to the free-text field, not the word 'other'"` — asserts the exact scenario that broke.

## Residuals — found, not fixed, explicitly flagged

- **`verify_evidence_chain()` is granted to `authenticated`, not `service_role`-only** (unlike `verify_ledger_chain()`, hardened in `20260709260000`). Initial framing ("no live consumer, so not affected") was **corrected by dev-lens**: the grant itself is the exposure — any authenticated session can call the RPC directly and loop a full-table scan of `chain_seq`/validity metadata (no PII) regardless of whether app code calls it. Low-value (metadata only) but live. Needs its own migration, not fixed here.
- **`participation_evidence_chain_seq_idx` is a plain index, not unique** — the ledger's equivalent (`credit_ledger`) was hardened to unique in the same 2026-07-09 pass for the same reason (`verify()`'s `lag() over (order by chain_seq)` needs no ties); the evidence migration copied the pre-hardening shape. Not exploitable today (identity column makes ties practically impossible) but should get the same fix when `verify_evidence_chain`'s grant is addressed.
- **`participation_evidence.registration_id` has no `ON DELETE CASCADE`** (unlike `registration_checkins`/`registration_roles`) — a registration with a real evidence row is now permanently undeletable via this FK too, independent of `credit_ledger`'s own NO ACTION pinning. **Trap for a future session**: `tests/cpd/attendance_issuance.rls.test.ts`'s `checkin()` helper only works around this by never calling the real check-in RPC (it inserts straight into `registration_checkins`, which `self_check_in`/`mark_attended` normally call but a raw insert bypasses entirely) — the moment anyone "improves" that helper to call the real RPC for fidelity, every `afterAll` registration delete in that describe block starts failing with `23503`.
- **`exportEvidenceActions.ts` inlines its own CSV builder** (not `lib/csv.ts`), so this session's BOM fix does not reach it — same mojibake risk for Chinese names in that export. Not touched (separate file, pre-existing, out of scope this pass).
- **`EvidenceExportButton.tsx` has the same missing `role="status"` gap** `CollegeExportButton.tsx` had before this session's fix — pre-existing, not a regression, not touched.
- **No manual browser click-through of the `data:` URL download itself.** Blocked all session by another Claude Code chat holding the only usable dev-server port (3100) in this project directory — Next.js 16 refuses a second instance in the same directory on any port. Component-level rendering is covered by real RTL tests; the specific thing only a browser catches (a large `data:` URL being blocked/warned by Chrome/Safari) rests on inference from the two already-shipping siblings using the identical mechanism, not on execution. Worth one manual click next session.
- **`regByUserId` is last-write-wins** if a user somehow has two registrations on one event (`registrations` is unique on `(event_id, email)`, not `(event_id, user_id)`) — dev-lens's own assessment: low likelihood, low impact. Not fixed.
- **No audit event for the export itself** — a regulator-facing PII package leaves no trail. Consistent with both sibling exports (not a regression). Candidate for a `DEFERRED.md` row, not fixed here.
