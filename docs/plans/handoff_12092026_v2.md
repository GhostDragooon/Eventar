## What shipped

### Commit 1 — `fca8232`: org-scope regression fix (Track A, the actual blocker)

v1's evidence layer accidentally reverted the 2026-09-10 authority sweep (`20260910000000_authority_sweep_org_scope.sql`, which moved event/check-in access from creator-scoped `created_by` to org-scoped `organisation_id`) in **three places**, all authored against a pre-sweep copy of the function/policy:

1. `participation_evidence_organizer_select_own` gated on `created_by` instead of org membership
2. `mark_attended`'s `CREATE OR REPLACE` (in v1's `20260912010000_checkin_writes_evidence.sql`) silently reverted to a `created_by` guard
3. **Critical, caught only in dev-lens review, not by my own first pass:** `participation_evidence_manager_select_all` used `app_private.is_manager()` (true for `organiser_admin` OR `eventar_staff`) with **zero organisation filter**. Since RLS policies are OR'd, any `organiser_admin` in *any* org could read *every* org's evidence, completely bypassing fix #1.

New migration `supabase/migrations/20260912020000_evidence_org_scope_fix.sql` fixes all three, restores `mark_attended`'s dropped "why" comments, adds an `organisation_id`-vs-event validation inside `record_participation_evidence` (the column is now load-bearing for RLS but was previously unvalidated), and hardens its own assertions to check policy *semantics* (the `qual` text) rather than just policy names — a name-only check is exactly what let bug #2 ship undetected the first time.

Test changes: `tests/rls/mark_attended.rls.test.ts` test 2 flipped from "same-org colleague denied" to "same-org colleague succeeds" (it was testing the *bug*, not the fix), plus a genuine cross-org `organiser_admin` fixture added so bug #3's class is actually exercised (an `organiser_member` cross-org fixture would pass even with that hole wide open — `is_manager()` doesn't match that role either way). New file `tests/rls/participation_evidence.rls.test.ts` covers org-member read, cross-org denial, self-read, and direct-write denial (42501-specific, not a bare "an error occurred" — Hard Rule 11).

### Commit 2 — `7dcc565`: frontend coherence mechanical pass (Track B)

Measured sweep against the token system in `app/globals.css`, not vibes — full sweep commands + hit counts are in the audit doc.

- 5 raw HTML form elements migrated to `components/ui/*` primitives: `RegistrationCloseEditor` (datetime input), `ManageWorkstation` (search input + sort — the sort control needed a full Base UI `Select`/`SelectTrigger`/`SelectContent`/`SelectItem` rewrite, not just a class swap), `ProfileClient` (biography textarea, which had hand-copied the Input primitive's className instead of using Textarea)

Omitting it silently shows the raw value ("most") instead of the label ("Most registered") — caught by a user-perspective cold-start review actually clicking through the app, not by any static gate. Fixed on the new `ManageWorkstation` sort control, and the same omission was found and fixed on three pre-existing consumers: `TeamClient.tsx` (role picker on live `/settings/team`), `GroupedSelect.tsx` and `TeammateInvitationForm.tsx` (currently unwired, no importer, fixed anyway)
- Also fixed: a `<label>` wrapping the Select's `<button>` trigger on `ManageWorkstation` — invalid HTML, silently shrank the clickable area to just the trigger text. Changed to `<div>`.

### Commit 3 — `374edf0`: two more phase-review findings

- `RosterClient.tsx`: "Check in →" rendered identically for a cancelled registration as for a live one, even though clicking it always fails (with a correct toast). Now disabled for `status='cancelled'` rows, reusing the existing `ELIGIBILITY_NOTE.cancelled` copy as the tooltip — matches the disabled-button convention already used two lines up for the chair/presenter toggles in the same component.
- `page.tsx` readiness strip vs `CpdAccreditationSection`: could show red "Unverified — body not authorised for this org" right next to green "Accredited — N credits already issued, locked" for the *same event*. Traced to two independent checks on the same `accrediting_body_id` — the strip resolves it against the org's *current* authorised-bodies list; the CPD section's "accredited" flag only checks that a body_id + hours are stored, regardless of current authorisation. Real scenario: the org's authorisation for that body lapsed *after* the event already issued credits under it. **Presented 4 resolution options to Ivan via AskUserQuestion** (connecting copy / reframe the strip cell / suppress the flag once locked / leave it) — he chose reframing the strip cell. When a body doesn't resolve as currently-authorised *and* credits are already issued, the cell now reads `Locked · authorisation lapsed · N credits already issued` (state `warn`, not `blocked`) instead of `Unverified / body not authorised for this org`. The "never was authorised, no credits yet" warning path is untouched.
