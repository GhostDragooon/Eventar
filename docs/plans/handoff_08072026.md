## Deviations from the literal plan text (all root-caused, none guessed)

The plan (`docs/plans/2026-07-04-cpd-sprint-2-implementation.md`) itself was updated in-place at every deviation point, with the reasoning inline — it is the authoritative record of *why*; this doc is the retrospective *what happened*.

1. **Task 1 split into 1a/1b.** Widening `Staff.role` to include `'eventar_staff'` breaks `tsc` at 9 staff-page call sites (two components declare their own local `'organizer'|'manager'` prop type). Verified zero Sprint 2 code actually needs the wider TS union — the DB-side gate reads the `staff.role` column directly via SQL, unaffected by the TS type. Shipped the `status='active'` gate now; deferred the union widen to Sprint 3 alongside the 5-role enum migration (same commit will touch those two files anyway).
2. **Task 2's test strategy corrected mid-task.** `app_private.require_active_staff` is confirmed empirically unreachable via PostgREST (`curl` → `404 PGRST202`, "Searched for the function **public**.require_active_staff" — `app_private` is never exposed). The plan's own footnote pointed at the wrong task for transitive coverage (said Task 6; Task 6's functions are self-actor, gated on `auth.uid()`, and never call this gate at all — Task 7's `transition_dsr` is the real first consumer). Task 2 shipped the migration + a one-time manual SQL backtest; Task 7 supplies the real automated regression coverage.
3. **A systemic grant-hygiene finding, discovered by Task 3, applied forward to every subsequent function.** Revoking `write_audit_event`'s grant from `authenticated` alone did nothing — this Supabase project has a schema-wide `ALTER DEFAULT PRIVILEGES` granting `anon`/`authenticated`/`service_role` EXECUTE on every new function at `CREATE` time, and the function also carried a bare implicit `PUBLIC` grant from Sprint 1. Every subsequent new definer function in the plan got an explicit `revoke ... from public, anon` (or `service_role`-only where there's no in-function actor check) added before it was ever built, not after.

## Defects found and fixed during execution

### Class 1 — migration filename drift, on every single migration
`apply_migration` has no version parameter; it assigns the remote version from server time at the call moment, ignoring the local filename entirely. First caught on Task 2 (local `20260704140000...` recorded remotely as `20260704162841`), then locked into the plan as a mandatory step for the remaining 8 migrations: call `list_migrations` immediately after every `apply_migration` and rename the local file to match exactly. All 10 reconciled; migration list 43/43 two-sided at the exit gate.

### Class 2 — the D1 grant gap recurred twice more, caught only by the exit-gate review
Task 3's own fix (revoke from `authenticated` + `PUBLIC`) never checked `anon`, and D1's own negative test only ever exercised `authenticated` — even though `createAnonClient()` was added to the test helpers in the very same sprint, for an unrelated task (Task 9). The Task 14 dev-lens review found, via live `pg_proc.proacl` query and an independent `get_advisors` scan, that `anon` still had `EXECUTE` on `write_audit_event` — a function with **zero in-function actor validation**, meaning any unauthenticated caller holding the public anon key (embedded in every client bundle, not a secret) could forge an arbitrary, correctly-chained audit event with false actor claims. Fixed (`1ed8b72`).

The fix-attempt for the same class of gap on `verify_audit_chain()` (Sprint 1, read-only) was **itself** a no-op on the first try: `revoke ... from anon, authenticated` did nothing, because that function's ACL carries a genuine bare `PUBLIC` entry — `anon`/`authenticated` inherit through `PUBLIC` regardless of a revoke targeted at them by name. This is the exact Task-3 lesson, recurred by the controller in the act of fixing the Task-3-adjacent gap. Caught only by re-querying `has_function_privilege` after the "fix" and finding it unchanged; the real fix (`revoke ... from public`) landed in a same-day follow-up migration.

**Both closures verified three ways**, not just re-read from migration text: a live `has_function_privilege` query (false/false/true across anon/authenticated/service_role), a fresh `get_advisors` security scan (both WARNs gone), and two new regression tests in `tests/audit/chain.test.ts` using the existing `createAnonClient()` helper — so this exact gap, and the exact mistake of revoking from named roles instead of `PUBLIC`, cannot silently reopen without a test failing.

### Class 3 — a real, undocumented behavioral regression in the self-check-in conversion
The user-lens review at the exit gate found that the per-IP→per-event rate-limit switch (intentional, documented) had an undisclosed side effect: an invalid/guessed registration code returns before `rate_limit_check` is ever reached — per-event keying requires a resolved event, so guessing had **no rate limit at all**, contradicting `lib/registrationCode.ts`'s own stated model ("887M codes — resists brute-force search ... paired with rate-limiting"). Practical exploitability was assessed as low (the code space + ~200 valid codes per event) but the regression was real and undisclosed.

Presented to Ivan with the tradeoff (a blanket per-IP limit can't be restored — that's exactly the venue-NAT false-positive problem the per-event switch exists to fix). Ivan chose the targeted fix: rate-limit only the invalid-code path, by IP. `self_check_in(p_code)` → `self_check_in(p_code, p_ip)` (old 1-arg overload explicitly dropped, not left reachable). `lib/rateLimit.ts`'s `getClientIp()` exported so the Server Action can thread the IP through. Verified with two new regression tests (the guess-cap actually triggers; a legitimate attendee sharing an IP with a capped guesser is unaffected) plus a re-run of the 200-concurrent burst test with all 200 calls sharing one simulated venue IP — still P99≈1370ms, confirming the venue-NAT fix wasn't undone.

### Class 4 — a test-harness bug in the self-check-in migration itself, caught by a mandatory pre-test smoke check
The original `self_check_in_fn.sql` used scalar `select ... into` bindings with a bare `event_id` column name — ambiguous against the function's own `RETURNS TABLE(..., event_id uuid)` OUT parameter of the same name. Fixed same-session (`fix_self_check_in_ambiguous_column`), and the lesson (table-alias every `select ... into` inside a function with matching OUT-parameter names) was carried forward explicitly into every subsequent function's instructions — none of them repeated it.

### Class 5 — a test-cleanup leak, caught by independent review
`self_check_in.rls.test.ts`'s `rate_limits` fixture rows leaked on every run: only 2 of 4 tests that indirectly create a `rate_limits` row (every `self_check_in` call does, unconditionally) pushed their key into the cleanup array. Reproduced live (5 pre-existing + 2 new orphaned rows from one re-run), fixed by tracking the key at fixture-*creation* time instead of relying on each call site to remember — closes the whole class of omission, not just the two instances found.

**Operational caveats, not defects (both already known from Sprint 1, both held true again this sprint):**
- `pnpm test:rls` in tight back-to-back succession can transiently exhaust local sockets. Held true again this sprint; same "run once, re-run once after a pause" discipline applied throughout.
- The pre-existing `app/events/new/NewEventForm.test.tsx` cross-file-pollution flake (only manifests in a full-suite run, never in isolation, unrelated to any file this sprint touched) recurred several times across the session's many full-suite runs — tolerated per the existing note, never investigated further (out of scope), and separately flagged as its own background task earlier in the session.
- **New this sprint:** the exit-gate's own burst-throughput test occasionally flakes (~1-in-4 runs observed, both by the controller and independently by the dev-lens reviewer) against its 2s P99 threshold, under real network conditions to the remote Seoul project — always well under 3s when it happens. Root-caused as network variance, not a functional regression (the underlying audit-chain lock-contention behavior, which is what the test exists to measure, showed no queue-depth growth pattern in any run). Not changed; tracked in `docs/DEFERRED.md` as Ivan's call.
