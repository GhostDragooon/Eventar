### Two findings the agents missed — found by running things, not reading them

1. **`seed.sql`'s blanket grant silently re-opened HIGH-1 on every `db reset`.** The migration's own self-verifying `DO` block passed — then `seed.sql` (which runs *after* migrations) re-granted `events` UPDATE and undid the lock. Caught only by actually running `supabase db reset` afterwards. **Without this fix, CI replay-from-zero and the future Singapore provisioning would both have produced an unprotected database.** `seed.sql` now re-asserts the events column lock alongside the existing `staff`/ledger ones.
2. **The local Docker stack was missing Stage 8 entirely** (Seoul had it, local did not) — so the demo, which targets local, would have run without the guard prod had.

### One regression I introduced and then caught

The `seed.sql` fix above **over-revoked**: it stripped `events` UPDATE from `service_role` too, so `seed-demo.ts` died with `42501` on the CPD-config write. `service_role` is the *trusted* server-side configuration path (the seed, the dashboard bulk actions, the edit fallback) and the migration never revoked it — only `seed.sql` diverged. Fixed in `e55248e`. Found by running the seed, not by re-reading grant assertions.

## The two things deliberately NOT fixed in code

Both are in `docs/DEFERRED.md` with re-entry criteria. **Neither is a bug to be picked up by the next session** — they are product decisions.

1. **No organiser↔body authorisation model.** The grant hole is shut, but the question the hole exposed — *which organisations may legitimately claim a relationship with which accrediting body* — is a B2 registry decision that needs the body conversation. Inventing one mid-hardening would have baked in policy nobody agreed to. Today nothing but the seed script can set these columns, so there is no live exposure. **Re-entry: before ANY surface lets a non-service-role actor set `events.accrediting_body_id`.**
2. **The credit window is a generous ±24h, not the real check-in window.** It kills the actual fraud (never attend, POST the emailed code days later) but is not semantically right — presence should mean the event's own check-in window. It cannot be tightened yet: **the demo fixture registers at Beat 3 and checks in at Beat 4 ~170 min BEFORE start**, and registration closes exactly when the check-in window opens, so the two beats cannot both sit inside a strict window. The agent's proposed `start − 2h` bound would have broken the demo outright. **Re-entry: when the fixture no longer needs both beats in one sitting, or `self_check_in` gains its own lifecycle guards.**
