**Two corrections found mid-build, both material**:
- The 2026-07-09 Sprint-3b design doc's literal `organiser_attested → body_confirmed` flip predates the `attendance_verified` tier (added 2026-07-24). The real gap was a path **from `attendance_verified` to `body_confirmed`**, not from `organiser_attested`.

The actual mechanism had to be a new ledger row referencing the original via `references_entry_id` — which is what doctrine's own R5 text already implied ("correctable via the existing compensating-entry path"), just not spelled out as the literal SQL shape.

**Two Minor findings from dev-lens review, both fixed before shipping** (no Critical/Important from either lens):
- Org-match check had no explicit `NULL` guard, unlike its own cited template (`verify_licence`). Unreachable today (both FK columns are `NOT NULL`) but added for defense-in-depth and convention consistency.
- The self-check DO block verified the confirm index's column/predicate shape but not that it was actually `UNIQUE` — a future edit could silently recreate it as a plain index, defeating the one structural guarantee this migration exists to add. Fixed.

User-lens review (live RPC calls against the real local database, full raw error inspection) found no issues — every error code/message is self-explanatory without reading source, idempotent re-confirm reads as success not error, and the one informational note (Postgres `RAISE EXCEPTION` surfaces as HTTP 500 through PostgREST regardless of the semantic error code — standard behavior, not specific to this migration) is a callout for whoever eventually builds a UI/integration against this RPC, not a defect.

## 4. What's NOT built — read this before assuming the M4/R5 gap is closed

- **No UI or queue.** Nothing surfaces to a body reviewer which provisional `credit_earned` rows exist or need confirming. A caller must already know the target `credit_ledger.id`. This is the real residual risk — the mechanism is reachable, the workflow around it isn't.
- **No check for a prior `credit_adjusted`/`credit_revoked` compensating entry** against the same original before allowing confirmation. Ledger stays fully reconstructable either way; whether confirmation should be blocked in that case is a real policy question, explicitly not decided here (flagged in the migration's own header).
- **The fuller Sprint-3b "Body reviewer accreditation workflow"** (submission → approval, before an event is even accredited) is a separate, still fully Stage-13-gated piece — this migration does not touch it.
- **Q37's grant-timing tension is flagged, not resolved.** See §2, decision 2.
