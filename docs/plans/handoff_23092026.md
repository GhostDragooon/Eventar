## 8. Q32 audience-boundary hardening (2026-09-24 addendum)

Context: on 2026-09-24 Ivan pushed back on the ship-with-fixes verdict. A second-pass dual-lens review (dev-lens + user-lens, both live-executed) confirmed dev-lens's original flag was correct AND surfaced a bigger mirror-image bug the first pass had missed. This section describes what was investigated, decided, and built on the addendum day.

### The two bugs

1. **Practitioner → organiser CTA trap (user-lens live-reproduced):** signed-in practitioner clicks "Start an Event" on the landing → `proxy.ts`'s staff-row lookup finds no match → session silently destroyed → lands on `/login?error=not_authorized` → static copy "Your email is not on the organizer list" renders before they've typed anything, keyed off the URL param. Reproduced against a real production-mode build with a real practitioner session.

2. **Organiser → practitioner wizard trap (dev-lens live-reproduced, NEW finding):** signed-in organiser navigates to any attendee-shell surface (their own `/events/[id]` preview, `/account/sign-up`, `/account/sign-in`) → silently funneled into `/account/complete` (the 4-step practitioner onboarding wizard) with zero framing that anything is wrong. Three independent entry points, all confirmed live. Not a security bug (RLS holds); a doctrine violation of "two audiences, two doors, never crossed."

### Ivan's model (locked via AskUserQuestion, 2026-09-24)

- **Organisers own the organiser side.** They have no attendee identity by design. Attendee surfaces must not silently render attendee chrome to a staff session or accumulate practitioner data under a staff UUID.
- **Three attendee check-in gates**, named by end-user (attendee) action, not by staff action: **self check-in** (accountholder pre-registered) · **walk-in** (guest OR existing user showing up on day) · **staff/exception route** (VIP or org-staff attending — separate business classification).
- **Any actor stratification lives in audit metadata, not in `source`** — one clean pathway vocabulary, no bloat.

### Implementation shape (locked via AskUserQuestion, not invented)

**Layer**: option 1 + option 3 together. Non-throwing helper in `lib/auth.ts` as single source of truth; shared route-group layout under `app/account/` for the hard redirect; shells own chrome using the same helper. NOT `proxy.ts` as the primary owner.

**Shell chrome for staff**: a "Programme" pill (same geometry as the existing Account pill, matching StaffShell's own naming for the dashboard row) + a small "You're viewing the public page" caption (hidden below `sm`).

**Manual-registration provenance**: source column stays as the single provenance signal; migrate the label `staff_walk_in` → `walk_in` (end-user-oriented, not staff-oriented); no new event type, no new column, no dual identity.

### What shipped on 2026-09-24

- `lib/auth.ts`: new `isStaffSession()` non-throwing helper. Same lookup shape as `requireStaff()` (active staff row for the session email). Fails-open on any error (returns false) since it drives UI framing + redirects, not authorization.
- `app/account/layout.tsx`: new shared layout for the whole `/account/*` tree. Calls `isStaffSession()` once; staff → `redirect('/dashboard')`. Individual `/account/*` pages stay dumb about the staff case.
- `getAccountMenuState()` in `app/account/actions.ts`: extended to return `isStaff: boolean` alongside the existing shape. Short-circuits the completeness/unlinked-count lookups for staff (no data needed).
- `components/shell/StaffProgrammePill.tsx`: new component. "Programme" pill → `/dashboard` + "You're viewing the public page" caption. Same tokens/geometry as the existing Account pill so the row layout is unchanged.
- `SiteShell`, `PublicShell`, `LandingNav` (via `LandingAuthPill`): all four attendee shells accept `isStaff`, render `StaffProgrammePill` when true.
- `app/(public)/events/[id]/page.tsx`: attendee-only decoration (name prefill, email prefill, unlinked-count nudge, `isAccountComplete` lookup) suppressed for staff sessions. Public event content itself stays intact — organisers can still preview their own events, just without attendee chrome overlaid.
- `app/(public)/events/page.tsx` + `app/(public)/checkin/confirm/page.tsx`: threaded `isStaff` from `getAccountMenuState()` through to the shell props (10 render sites on the checkin/confirm page's various `Empty` and `PublicShell` calls).
- `app/events/[id]/checkin/actions.ts`: `walkInRegisterAndCheckIn()` now explicitly writes `source: 'walk_in'` (was defaulting to `'self_registration'` — a lie about provenance).
- `supabase/migrations/20260924000000_registrations_source_walk_in_rename.sql`: new migration. Renames the `source` CHECK constraint value `staff_walk_in` → `walk_in` (end-user-oriented, per Ivan's model). Migration applied to local stack and self-check passed.

- `tests/rls/registrations_link_immutability.rls.test.ts`: one assertion updated (`'staff_walk_in'` → `'walk_in'` for the trigger-blocked update test).

### What was investigated but NOT built (with reasons)

- **Dedicated `audit_events` row for the registration step** (option B from the audit AskUserQuestion): Ivan chose "enough as-is" — `source` column + existing check-in `audit_events` row (via `mark_attended`, which captures `auth.uid()` and `actor.role`) tell the truth as a chain, no bloat.
- **New column `registered_by_staff_id`** (option C from same question): rejected same reason.
- **Exception-vs-walk-in door toggle in the staff UI** (option 2 of source labeling): Ivan chose option 1 — one clean pathway vocabulary. Distinguishing "ordinary walk-in" from "VIP/late/waived/staff-entered exception" belongs in audit metadata, not in the `source` enum.
- **`proxy.ts` staff-allowlist edits**: rejected as the primary layer per Ivan — `proxy.ts` is a staff-allowlist gate (no session or not on staff list → sign out and send to /login), and the `/account/*` rule is inverted and softer (staff session → redirect to /dashboard without signing out). Folding both into one file widens blast radius.

### Provenance-chain honesty (post-2026-09-24 state)

For any walk-in registration created via `walkInRegisterAndCheckIn()`:
1. `registrations.source = 'walk_in'` — set explicitly at INSERT, immutable thereafter per the existing set-at-insert-only trigger.
2. `email_log` row with `status = 'skipped'` — records the deliberate omission of the confirmation email (attendee is physically present, no email needed).
3. `mark_attended` (called immediately after the INSERT within the same Server Action) writes an `audit_events` row capturing `auth.uid()` (the staff member's UUID via review-mode-aware `resolve_actor()`) and `actor.role`.

The chain doesn't lie. No dedicated "staff registered this attendee" event exists as a separate concept, because the action ALWAYS immediately checks in and the check-in event's actor metadata is the same staff.
