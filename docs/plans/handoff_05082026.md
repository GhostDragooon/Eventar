## 2. The four findings the audit began with

1. **There was no trigger, and the route's own header said there was.** `vercel.json` was reverted in `72cda80`; the comment claiming it was the shipped trigger outlived the file. No pg_cron job either. Deploying on the strength of that comment ships a dead scheduler that fails silently.
2. **A failed send could never be retried.** `email_log_dedup_idx` had no status predicate, so any existing row → 23505 → skip. One transient Resend error lost a recipient's mail permanently — and `runBulkSend` counted it as `skipped`, which `formatSendResult` renders as **"already sent"**. Rule 12 inverted. (`email_log_queued_idx` exists for a "Phase 9 pg_cron will poll these" sweeper that was never built.)
3. **The batch cap bounds events, not recipients**, against a route that had no `maxDuration` (host default 10–15s).
4. **"The next tick picks them up" was false.** Selection is purely time-based, so the same arbitrary first 20 were re-picked every tick; 20 long-window surveys could starve a reminder permanently. The existing test proved the cap, never the recovery.

## 3. What the three-lens protocol found — in this same day's work

**Both lenses found real defects, and one invalidated a decision Ivan had already made.**

- **The migration's central premise was false.** It claimed a `failed` row proves nothing was delivered. [lib/resend.ts:80](../../lib/resend.ts) catches network/connection errors and maps them into the same `{ error }` shape as a 4xx — so a message Resend *accepted*, whose response was lost in transit, is recorded `failed` and (now that failed rows retry) re-sent. A second QR pass to a regulated professional. **Ivan approved the narrow fix specifically because it had no duplicate window; that was my error, not his.** Closed provider-side with Resend's `idempotencyKey` keyed on `${eventId}:${purpose}:${registrationId}` — the same triple the index keys on. Both properties now hold instead of the second being assumed.
- **The retry cap was placed in the shared send core**, so the manual "Send reminders now" button — the operator's only rescue lever — became a silent no-op for exactly the recipients needing rescue. **Sixth instance of "a control one layer above where the write actually happens"** (see `handoff_04082026.md` §6). Fixed: the Server Actions pass `{ manual: true }`.
- **The other session's incoming lint rule caught a live bug of mine.** The attempt-cap query destructured `data` without `error`; a failed read produced an empty attempts map, silently dropping the cap for *every* recipient. It then pointed at a pre-existing sibling: `readRecipients` collapsed a query failure into `[]`, which callers read as "nobody to email" — a DB blip mid-tick would skip an entire event's reminders and report *"No registered attendees yet."* Both fixed.
- **One of my own tests was vacuous** (rule 9): the `email_log` select mock discarded filters, so deleting `.eq('status','failed')` from production left every test green. Fixed and **mutation-tested** — the mutant now fails.

The user-lens also **corrected the controller's framing**: a dead scheduler does *not* destroy credit. Staff hold the registration code and can check anyone in from the Roster (`RosterClient.tsx`), so it degrades the door to manual lookup. Serious operational failure, not a credit-integrity one.

## 3b. The fix for §3 was itself broken — and rule 14 came out of it

Asked "so what do we do about the false premise", the answer was to re-run the skipped step over every other claim made that day. Three failed the test; one was a **live bug in the idempotency fix itself**.

`idempotencyKey` closed the duplicate risk, but Resend rejects a reused key whose payload differs (409) — and the reminder embedded `countdownLabel`, derived from `Date.now()`, landing in both the pill and the `<Preview>` line. Two ticks five minutes apart therefore differed, so **every reminder retry would have 409'd, failed, retried, 409'd, and given up after three** — while the UI said "retrying automatically". The fix for one layer broke the layer beside it.

An agent established the extent before anything was changed (rule 14's first real use), and it paid: the survey path is **fully deterministic**; the QR PNG is **byte-stable** (verified empirically — pngjs emits no `tIME` chunk); `countdownLabel` was the only clock-volatile field; the confirmation email is never retried and correctly carries no key. It also found a trigger that would have been missed — **a staff edit to the event between two ticks** changes title/venue/time and breaks the key just as effectively, which no amount of clock-determinism prevents.

Resolved both ways (Ivan's call): the scheduler now renders a stable `SCHEDULED_COUNTDOWN_LABEL` while the manual path keeps its live countdown (it is never retried), **and** a 409 is treated as already-delivered — keyed on the HTTP `statusCode` now surfaced through `SendEmailResult`, not on a guessed string. Both guards are mutation-proven: reverting either makes a test fail.

**A test had to be fixed before it could be believed.** The first payload-stability test passed immediately — `renderReminderEmail` was mocked to a constant, so it could not observe the volatile field at all. It now renders from its props. Worth remembering: a green test against a constant-returning mock proves nothing.
