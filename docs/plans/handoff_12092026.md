## What shipped

The complete participation evidence layer per ADR-0003 dual-package segregation: every successful check-in (self-serve + staff) now writes an immutable `participation_evidence` row alongside the existing `registration_checkins` operational mark. Evidence is the durable, tamper-evident audit trail bodies ask for; attendance (`registration_checkins`) remains authoritative.

### Migration 1: `20260912000000_participation_evidence.sql`

New `participation_evidence` table with K2 integrity substrate:

- **Schema:** 22 columns — `id` (uuid PK), `chain_seq` (GENERATED ALWAYS AS IDENTITY, UNIQUE), `organisation_id`, `event_id`, `occurrence_id` (nullable), `registration_id` (nullable), `user_id` (nullable), `evidence_type` (check_in / check_out / session_mark / correction), `capture_method` (qr_scan / staff_scan / self_serve / manual_entry / ble_proximity), `source` (live_checkin / staff_attestation / device_attestation / administrative), `captured_at`, `attestation_strength` (strong / standard / weak), `actor_id` (nullable), `device_metadata` (jsonb, NOT NULL default `{}`), `source_nonce` (nullable, dedup), `previous_evidence_id` (self-ref FK for corrections), `local_unlock_metadata` (jsonb, nullable, reserved for ADR-0003 §1), `prev_hash` (bytea), `hash` (bytea NOT NULL), `created_at`
- **Unique constraint:** `(registration_id, occurrence_id, evidence_type) WHERE previous_evidence_id IS NULL` — one original per (reg, occurrence, type); corrections unconstrained
- **Chain mechanics:** advisory lock `pg_advisory_xact_lock(hashtext('participation_evidence_chain'))`, SHA-256 via `pgcrypto.digest`, same K2 pattern as `credit_ledger`
- **SECURITY DEFINER writer:** `record_participation_evidence(15 params)` — only write path; idempotent on `source_nonce`; audit event (`evidence_recorded`) written last (Hard Rule: audit insert last)
- **Chain verifier:** `verify_evidence_chain()` — same shape as `verify_ledger_chain()`, returns broken-link rows
- **Grant posture (Hard Rule 11, lifecycle):** `REVOKE INSERT, UPDATE, DELETE FROM anon, authenticated, service_role`; then `GRANT DELETE ON participation_evidence TO service_role` (retained for DSR / test teardown, not a permanent ledger)
- **RLS policies:** `organizer_select_own` (via `events.created_by = current_staff_id()`), `manager_select_all` (via `app_private.is_manager()`), `self_read` (`user_id = auth.uid()`)
- **Assertions:** 10 grant/policy assertions at deploy time (`DO $$` block)
- **seed.sql:** local-stack grant-back block (CLI 2.109 pattern) — mirrors the revoke/re-grant correctly

### Migration 2: `20260912010000_checkin_writes_evidence.sql`

`CREATE OR REPLACE` of both `self_check_in` and `mark_attended` to call `record_participation_evidence()` after the `registration_checkins` write:

- **Function bodies based on `20260815040000`** (the multi-occurrence fix), NOT `20260815010000`. This is the critical detail — the earlier session that wrote this migration initially based it on the wrong version, reintroducing the `v_status = 'attended'` short-circuit that killed multi-occurrence check-ins. Completely rewritten in this session to use the correct base.
- **Evidence write is best-effort:** wrapped in `BEGIN...EXCEPTION WHEN OTHERS THEN RAISE WARNING '... (SQLSTATE %): %', sqlstate, sqlerrm`. Evidence failure never rolls back the check-in.
- **self_check_in:** `evidence_type='check_in'`, `capture_method='self_serve'`, `source='live_checkin'`, `attestation_strength='weak'`
- **mark_attended:** `evidence_type='check_in'`, `capture_method` derived from `p_method` ('qr'→'qr_scan', 'manual'→'manual_entry'), `source='staff_attestation'`, `attestation_strength='standard'`
- **Assertions:** multi-occurrence fix preserved (no `v_status = 'attended'` short-circuit), `record_participation_evidence` called from both, ACLs intact

## Next logical steps

The evidence layer is the foundation. Logical follow-ons per the plan:

1. **Correction workflow** — new `participation_evidence` row with `previous_evidence_id` linking to the original (schema already supports it; no UI yet)
2. **`verify_evidence_chain()` surfaced to organiser** — a simple "chain verified" indicator alongside the evidence count
3. **Sufficiency rule engine** — `attendance_assessments` table evaluating evidence against body requirements
4. **Device attestation source** — BLE proximity or device-signed nonces (the `source_nonce` + `device_metadata` columns are reserved for this)
