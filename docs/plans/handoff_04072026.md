## Defects found and fixed during execution (all pre-commit — none shipped with the bug present)

Three real defects surfaced by following the plan's own verification steps, each root-caused against live database state (queries to `pg_proc`/`pg_roles`/`information_schema`, Postgres and API log inspection) before any fix was applied — none were guessed or worked around silently:

1. **`ALTER FUNCTION ... OWNER TO audit_writer` failed** (`permission denied for schema public`). Root cause: Postgres requires the *target* role of an ownership transfer to hold `CREATE` on the object's schema at the moment of transfer — a requirement distinct from needing it afterward. Fix: bracket the transfer with a grant-then-revoke, so `audit_writer`'s standing privileges end up exactly as designed (SELECT+INSERT on `audit_events`, nothing more) — confirmed live via `has_schema_privilege('audit_writer','public','CREATE') = false` post-migration.
2. **The audit-chain smoke test then failed** (`permission denied for schema extensions`). Root cause: `compute_audit_hash()` isn't `SECURITY DEFINER`, so it executes as whatever role is active during the INSERT — which becomes `audit_writer` once it fires from inside the now-`audit_writer`-owned `write_audit_event()`. That role had never been granted access to `extensions.digest()`. Fix: grant schema `extensions` USAGE + EXECUTE on the specific `digest(text,text)` overload actually used (pgcrypto also exposes a `digest(bytea,text)` overload that isn't needed).
3. **The concurrency test's literal 200-way `Promise.all` overwhelmed the local Node/undici connection layer** (158/200 client-side `TypeError: fetch failed`, with the live Postgres and API logs showing zero server-side errors, zero connection-limit or lock-timeout pressure during the same window — confirmed by direct log inspection, not assumed). Fix: batch the 200 writes into concurrent chunks of 20 (empirically the reliable local ceiling — 30 already showed one failure in isolation). Each batch of 20 still genuinely exercises the advisory-lock serialization under real overlapping Postgres transactions, which is the actual property under test.

**Operational caveat, not a defect:** running `pnpm test:rls` in tight back-to-back succession (several full runs within a few minutes, as happened during this session's own debugging) can transiently exhaust local client-side sockets and produce spurious failures with no server-side cause — confirmed by pulling live project logs during a failing run and finding nothing abnormal. Two clean 17/17 runs after a natural pause confirmed this. Run it once per session; if it fails, wait briefly and re-run once before concluding there's a real regression.

## Carried forward (not fixed this sprint — explicitly tracked)

### `write_audit_event` has no caller-identity check
Flagged by the dev-lens review. The function is `SECURITY DEFINER`, owned by `audit_writer`, and grantable via PostgREST RPC to `authenticated` — but nothing inside it verifies that a caller-supplied `p_actor_user_id`/`p_actor_role` actually matches the calling session. A malicious authenticated user could call it directly and forge a legitimately hash-chained row with false actor claims. This does **not** compromise the chain's tamper-*evidence* (Sprint 1's actual design goal, and the thing `verify_audit_chain()` proves) — it's a gap in audit *authenticity*, which was always intended to be enforced by Sprint 2's `withSecurity` Server Action wrapper being the sole real-world caller, deriving actor fields server-side from the authenticated session rather than trusting client input. **Needs an explicit decision at Sprint 2 start**: either restrict the grant once the wrapper exists, or document the direct-RPC-forgery path as an accepted residual risk in the security middleware doc.

### Two performance-only advisor warnings
`multiple_permissive_policies` and `auth_rls_initplan` on `consent_records`/`data_subject_requests`/`users` — overlapping self+staff SELECT policies and an unwrapped `auth.uid()` in policy predicates. Neither is a correctness issue, neither was required by the plan or BASELINE-DELTAS, both are cosmetic at current data volume. Candidate for a policy-consolidation pass once real user volume exists — not blocking anything.

### Engineering debt, pre-existing, unchanged this sprint
- Vitest flake in `app/events/new/NewEventForm.test.tsx` (save-confirmation timing) observed once under parallel test-worker load during this sprint's regression gate; reproduced 0/5 times in isolation and 0/2 times on full-suite re-run. Pre-existing, unrelated to any file this sprint touched (nothing under `app/`/`components/` was modified). Not investigated further — flagging for whoever next touches that test file.
- The live `audit_events` table now carries several hundred synthetic rows from this sprint's own smoke tests and repeated `test:rls` runs (event types prefixed `sprint1_*` and `chain_test_*`). Expected and harmless — the table is insert-only by design, and no application role (including `service_role`) can delete from it — but worth knowing when later reading the Sprint 1-era audit trail as a demo or a reference.
