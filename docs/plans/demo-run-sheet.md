## Pre-demo setup (30 min, scripted)
0. **Refresh the demo worktree before the first run after any code change lands on `main`**: `git -C /Users/ivan/Eventar-demo checkout --detach main` (or the specific SHA). The worktree serves whatever it's checked out to, independent of the main checkout's `:3000` — the CPD issuance code (Stages 1–6) is now genuinely committed, so a fresh checkout is all that's needed; no manual file copying.
1. Local Supabase stack up (`supabase start`) → `db reset` replays migrations + seed (replay proven 2026-07-10; **app-against-local-stack proven end-to-end 2026-07-11**: landing → magic link via Mailpit → PKCE → staff dashboard, all green). Note: the committed seed's staff row is a placeholder literal (`MANAGER_EMAIL`) — unusable for login; `seed-demo.ts` owns creating the real demo operator (verified working: `demo-staff@local.test`).
2. Run `scripts/demo/seed-demo.ts` (built — see Milestone A) **as the LAST prep action, immediately before going live** (see the timing rule below — the registration clock starts counting from the moment you seed): default org (no separate "Demo CPD Alliance" org — Task 2 shipped against the executable plan's simpler no-org-creation shape; nothing currently displays an org name to attendees, so this is cosmetic), event **"Clinical Update Seminar 2026"** (2 agenda blocks, 3 speakers, **pre-created as a draft** so Beat 2 demos the *publish* moment, not form-filling; also CPD-configured — 3 hrs @ HKAM), 6 plausibly-named fake attendees, one pre-registered. That one (Karen Lau) also gets a real account + a **verified HKAM licence** — the seed prints `CPD credit: 3 hrs @ HKAM — Karen Lau has a verified licence…` — so *her* check-in specifically is the one that auto-posts a real credit at Beat 4; the other 5 attendees have no licence and would correctly get skipped if checked in (a real, working guard — not a demo gap). The seed prints a **`Reg. closes: … (N min from now)`** line — that N is the deadline you have to reach Beat 3 by. **Fixture timing rule (offset widened to 180 min on 2026-07-18 — the earlier 45- and 90-min figures were both too short, confirmed live):** event start = now + **180 min**. Registration closes UNCONDITIONALLY once the check-in window opens (`start − CHECKIN_OPEN_MINUTES` = 60 min — `lib/lifecycle/eventLifecycle.ts`, G11), regardless of `registration_close_at`, so the registration-open window is exactly `(offset − 60)` min wide. A 45-min offset opened the event already past that boundary (Beat 3 failed on arrival); 90 min left only a ~30-min window that this very prep block consumes, so registration could still be closed by the time you reach Beat 3 live. 180 min leaves a **~120-min window** that comfortably outlasts prep + the 15-min demo. Self-check-in (Beat 4) is unaffected by any offset — it's gated only by the static `events.checkin_modes.self_serve` flag the seed sets, not by the lifecycle clock — so it works regardless of elapsed time, which is why a large offset has zero downside.
3. Demo server: **run from the demo worktree** — `bash /Users/ivan/Eventar-demo/scripts/demo/dev-local.sh` (or the `demo-local` launch config), port 3100. It must NOT run from the main checkout: Next 16 allows one dev server per project directory, and the always-on `:3000` server holds that lock (**that server also points at live Seoul, not local** — a second, independent reason never to demo from it). The script derives Supabase env from the running local stack. Next 16 dev already listens on the network interface (boot log prints the `Network:` URL) — for LAN phone scanning just set **`DEMO_SITE_URL=http://<laptop-LAN-IP>:3100`** before start so `lib/origin.ts` mints reachable QR URLs, and accept the macOS firewall prompt in prep, not live. Local-stack auth redirects for `:3100` (incl. a `192.168.*.*` wildcard) are already in `supabase/config.toml`. **CPD credit issuance defaults ON** (`CPD_ISSUANCE_ENABLED` fails open — unset or `'true'` both work; only an explicit `'false'` disables it) — nothing to set for the demo, but if Beat 4.6's ledger readout comes back empty, this env var is the first thing to check.
4. **Pre-authenticate staff sessions on laptop + tablet** — login is email-OTP (`signInWithOtp`); on the local stack the OTP mail lands in the local mail catcher, fine in prep, embarrassing live. Sessions persist through the demo.
5. Email beat prep — generate **two rendered templates** with `DEMO_SITE_URL=http://<laptop-LAN-IP>:3100 pnpm exec tsx scripts/demo/render-emails.ts` (the same LAN IP as step 3, so the reminder's QR is reachable from the staff tablet; it defaults to `http://localhost:3100`, which the tablet cannot reach across the LAN). Outputs land in the git-ignored `scratch-demo/`: open `scratch-demo/confirmation.html` in a laptop tab (Beat 3 — deliberately carries NO code/QR; that's a talking point, see Beat 3), and `scratch-demo/pass-reminder.html` *for the pre-registered attendee* on the **demo phone** (Beat 4 — this is the pass: personal QR + manual code, keyed to the `DEMO PASS CODE` the seed printed). The script already substitutes a **data-URI QR** for production's `cid:` mail attachment so the image displays in a browser. Rendering reads the current seed, so **re-render after every seed/reset** (codes change — see the reset procedure). devEmailStub stays — no cutover while D0 holds.
6. Tablet on the check-in roster page; phone with the rendered pass ready; poster PDF on screen or printed.
7. Backup for demo-day failures: screen recording of Beats 2–5 on the laptop, ready to play if wifi/hardware dies (Beat 2's Mapbox geocoding and any live typing are the fragile bits).

## Reset procedure (between rehearsals/meetings)
`scripts/demo/reset-demo.ts` (built): local stack only — tear down the demo rows, re-seed, verify chains green. **Reset regenerates the event and every registration code**, so anything rendered from the previous seed is now stale: after each reset you MUST re-run `render-emails.ts` (step 5) and re-note the new `DEMO PASS CODE`/window the seed prints — the phone's old QR and the memorised code will "Code not recognised" at Beat 4 otherwise. Reset also **re-declares and re-verifies Karen Lau's HKAM licence** against a fresh auth account each time (her old one, and any credit it earned, becomes permanent local-project residue — harmless, matches the append-only ledger's own design). **Never run demo flows against the live Seoul/Singapore projects: `credit_ledger` is append-only by design; demo rows there would be permanent residue in a regulator-facing table** (reset-demo enforces this with a hard `localEnv()` guard that throws on any non-127.0.0.1 target).
