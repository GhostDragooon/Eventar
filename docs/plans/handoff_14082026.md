## 8. Major finding: review mode couldn't actually complete its own stated purpose — found and fixed

Backtesting the full lifecycle (register → publish → check-in → credit → reconcile) surfaced this by just clicking the real "Publish event" button, which 500'd with "Cannot publish: event not found or not owned by you" — regardless of true ownership.

**Root cause, confirmed by direct RPC test (curl, service-role key, no session):** `lib/supabase/server.ts` deliberately routes `supabaseServer()` to the **service-role client** under review mode (so staff pages render with real content instead of an empty RLS-filtered view — see that file's own comment). But `publish_event`, `mark_attended`, `set_event_cpd_config`, and `event_registration_eligibility` all resolve their acting staff member via `app_private.require_active_staff()`, which reads the JWT's `email` claim — and a service-role call carries no such claim, so it always raised `42501`, independent of any real ownership fact.

**Full extent, confirmed empirically** (not just reasoned): all four functions reproduced the exact same failure via raw service-role RPC calls before any fix. These are the *only* `require_active_staff()`-calling functions reached via `supabaseServer()` from live app code — everything else already uses the admin client directly or (for `create_event_with_blocks`/`update_event_with_blocks`) already had the fix this migration applies elsewhere.

**Production is unaffected** — a real logged-in staff member always has a real session with a real email claim, so `require_active_staff()` already resolves correctly for them. This bug is confined to `EVENTAR_REVIEW_MODE`, which is structurally impossible to enable in a production build (`lib/reviewMode.ts` checks `NODE_ENV==='production'` first, unconditionally).

**Fix** (migrations `20260814020000`, `20260814030000`): a shared `app_private.resolve_actor(p_actor_override, variadic p_roles)` helper — the exact pattern `create_event_with_blocks` already used for this exact problem, generalised into one place instead of copied four times. Honoured **only** when `auth.role() = 'service_role'`, which a real authenticated user's JWT cannot forge (verified by PostgREST against the signing secret before the function ever runs) — so the override is structurally inert for every production caller. The override id is still validated against `staff.status`/`staff.role` exactly like the session path; it skips only the JWT-email lookup step, not the authorization check itself. Considered and rejected a session-emulation fix (minting a real JWT for the review identity) as riskier to get right blind and out of scope for touching the auth mechanism as a side effect — flagged as the alternative in the migration's own header, not built.

**Verified working end-to-end, live, not just via the RPC**: publish → check-in (manual code entry) → `credit_earned`/`attendance_verified` row posted to `credit_ledger` at `hours=3` → CPD-config freeze trigger correctly re-engaged ("1 credit has already been issued... accreditation is locked") → registration on a second event, confirmed via the DB and the "YOU'RE REGISTERED" UI state. Every step confirmed by querying the database directly afterward, not by trusting a screenshot.

One related internal call site left unfixed on purpose: `create_event_with_blocks`'s own internal `perform public.publish_event(new_event_id)` (when an event is created already-published) doesn't pass an actor override, and would hit the same wall under review mode — but grepped the actual form components and confirmed no live UI path ever submits `status: 'published'` at creation time (the schema defaults to `'draft'`; publishing is always a separate, explicit action). Genuinely dead code path today, not fixed to avoid touching something unreachable.
