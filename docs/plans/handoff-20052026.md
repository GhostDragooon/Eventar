## Key learnings to carry forward

### 🔴 PostgreSQL RLS + `RETURNING` is a footgun

Anon has INSERT-only on `registrations`. Postgres requires SELECT privilege to use `RETURNING`. The Supabase JS client's `.insert(…).select(…)` chain compiles to `INSERT ... RETURNING`. Result: insert succeeds at the WITH CHECK level but the RETURNING phase fails with the misleading "new row violates row-level security policy" error.

**Rule:** if a table has INSERT but not SELECT for the calling role, **never** use `.select()` after `.insert()` — use the admin client for the insert, or drop `.select()` and look up the row via another path.

This pattern bit us in two places (B1 capacity count + B2 register insert) and both were caught only by the live-DB backtest, not by static code review.

### 🟠 Live-DB backtest > browser smoke for RLS/data-path bugs

The browser smoke would have surfaced "registration failed" but not why. The live-DB backtest isolated each layer (RLS policy evaluation, WITH CHECK vs RETURNING, cascade behavior, trigger firing) and produced a 7-row pass/fail table. ~20 minutes; equivalent to ~2 hours of "submit, fail, log, repeat" in the browser.

**Rule:** for any data-path feature, write a live-DB backtest as part of the implementation, not after.

### 🟡 Implementation notes that update *as you build* surface bugs

V2 (page-count admin) was caught while writing the deviation note — the act of narrating the choice made me re-examine the line. V3 (Server Action admin) was caught by the backtest. Together: 3 of the 4 critical bugs found in this session came from writing things down, not from reading.

### 🟡 Misleading error messages are worse than no error messages

`"new row violates row-level security policy"` was 100% true but completely wrong as a diagnostic. The actual cause was a SELECT-permission failure on the RETURNING phase. Postgres collapses both into the same error string. Trust nothing.
