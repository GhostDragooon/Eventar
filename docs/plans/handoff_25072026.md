## The four real schema mismatches the build itself caught (not the plan, not either review round)

1. `entry_type='attendance'` doesn't exist (CHECK only allows `credit_earned|credit_adjusted|credit_transferred|credit_expired|credit_revoked`) — Stage 1's idempotency index was silently inert; re-keyed in Stage 2's corrective migration to `entry_type='credit_earned' AND attestation_status='attendance_verified'`.
2. `attestation_status` CHECK lacked `'attendance_verified'` — widened (Ivan-confirmed live in conversation) since venue-captured attendance is a genuinely distinct, stronger provenance tier than `organiser_attested`.
3. `public.users` has **no email column** (mirrors `auth.users` by `id` only) — identity resolution (`registration.email → user`) had to move into the `award_attendance_credit` SECURITY DEFINER function itself, which can read `auth.users`; the TS layer can't.
4. `practitioner_licences.status` has no `'active'` value (`declared|verified|lapsed|revoked|superseded`) — the good-standing state is `'verified'`; the definer function originally filtered on `'active'` and would never have matched any real licence. Corrective migration `20260724170650`.

Each was caught by checking the live schema before writing dependent code — worth internalizing for Stage 6/7: **check the actual schema/runtime behavior before trusting the plan's assumptions, every time**, not just when something looks surprising.

## Stage 4 — why "live-browser-proven" is doing real work in that phrase

Stage 4's own script-level verification (seed prints the right banner, DB has the right rows) looked complete and was **not** — it only proved the fixture was assembled correctly, not that the automatic issuance mechanism actually fires. Driving the real `/checkin/confirm` page in a browser and clicking the real "Confirm I'm here" button surfaced two defects that no static check caught:

1. **Wrong Supabase project.** The main checkout's `.env.local` points `NEXT_PUBLIC_SUPABASE_URL` at **Seoul**, not the local stack — so `pnpm dev` / the `eventar-dev` launch config talks to the wrong database entirely. The demo scripts are local-only (`localEnv()` hard guard), so a registration created by `seed-demo.ts` will never resolve against Seoul. Fix: use the `demo-local` launch config (`:3100`, derives env from `supabase status` live) — but that runs from the **`/Users/ivan/Eventar-demo` worktree**, which didn't have this session's Stage 2/3 code. Synced `app/(public)/checkin/confirm/actions.ts` + `lib/cpd/awardAttendanceCredit.ts` into the worktree (uncommitted there — see Operational notes).
2. **The kill switch defaulted OFF.** `awardAttendanceCredit.ts` originally required `CPD_ISSUANCE_ENABLED === 'true'` to proceed — but nothing anywhere sets that env var, so every award silently skipped, and (worse) the skip wasn't even logged, since the kill-switch branch returned before any `console.info` call. A "kill switch" that has to be discovered and explicitly turned on before it ever works isn't a kill switch, it's an invisible opt-in flag. **Inverted to fail-open** (`=== 'false'` to disable), added the missing skip-log line, added a regression test (`lib/cpd/awardAttendanceCredit.test.ts`: "kill switch unset (undefined) → issuance proceeds, RPC IS called").

Re-verified after both fixes, live: reset → published the event via a real `signedInClient` RPC call (not a raw SQL UPDATE) → clicked the real button → `credit_ledger` on the local stack shows a real `credit_earned | attendance_verified | 3 hours | HKAM` row → `verify_ledger_chain()` returns clean → the dev server's own log shows `[cpd] attendance credit { result: 'issued' }`.
